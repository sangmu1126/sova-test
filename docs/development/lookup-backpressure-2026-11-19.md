# 조회 backpressure와 복원 스냅샷 후속 개발 기록

2026-11-19 · 시작 `a088cb623b1680d5e6fcdf4ad578a5bbf5f10745`.

## 목표와 선택

직전 정상 전환에서도 source 503 뒤 키 조회가 반복되면서 클라이언트의 8회 한도를 소진한 주문이 있었다. 코드를 확인한 결과 POST의 503에는 `Retry-After: 1`이 있으나 GET의 503에는 없었다. 클라이언트는 이미 서버 안내를 지키므로 재시도 횟수·시간을 늘리는 대신 GET에도 같은 안내를 주는 선택적 시험 경로를 추가했다.

이것은 HTTP backpressure이며 서버 측 쓰기 대기·내구성 큐·서버 접수 영수증이 아니다. 기존 앱이나 제품의 일반 API에 적용하지 않는다. 기존 v3 기본 동작은 유지하고 `ready_backpressure`만 v4 프로필의 1초 안내를 사용한다. 인증·범위·충돌 거부, 권위 있는 404, 멱등 키와 payload 결속, 기존 쓰기 차단·승인·효과 원장을 유지한다.

실제 HTTP response hook에서 받은 안내를 trace에 추가했다. 고정 이미지의 BoundedOrderClient 자체는 수정하지 않는다. 실패한 최초 전송, 호출 내 재시도, 부하 종료 후 복구, 완료 뒤 probe를 구분한다. 한도 소진을 후속 복구로 성공 처리하지 않는다.

다른 개인 작업 트리는 `e8c6652b0cb82ae1918fb838cb4133ae8c2e36ac`로 깨끗했다. 원래 비교 대상 fixture와, 이후 발견한 `postgres_handoff_probes.py`는 그 세션의 변경 경로에 없었다. probe의 수정 전 바이트도 양쪽에서 같았다. 해당 작업 트리·팀 저장소·공유 인프라는 수정하지 않았다. 로컬 범위 공지는 다른 세션의 승인이나 잠금으로 간주하지 않는다.

## 첫 구성 요소 실패와 수정

`60da0b8`에서 구성 요소 44건 중 42건이 통과하고 실제 DB 시험 2건이 실패했다. 시험이 접속 시작 단계의 거부를 `InsufficientPrivilege / 42501`로 가정했으나 이 드라이버는 `OperationalError`로 반환했고 SQLSTATE가 없었다.

`b30bfc9`에서 앱의 실제 정상 연결을 먼저 확인하고, 서버의 CONNECT 권한 false와 실제 접속 실패를 함께 대조하도록 바꿨다. SQLSTATE를 만들어 넣지 않는다. 권한 복구 뒤의 실제 404·멱등 재제출·충돌 409·원래 50행도 검증한다. 새 별도 출력 경로에서 44건 모두 통과했다. 첫 실패·원문·커밋은 보존했다.

38건의 별도 단위 실행은 44건 묶음과 겹친다. 82건으로 합산하지 않는다. 44건에는 실제 TLS DB 계약 2건, 새 실제 loopback TCP 대기·기한 시험 2건, 기존 스트리밍 취소·응답 유실 TCP 회귀 2건도 포함한다. 통제한 TCP 응답과 실제 DB·클러스터 이전은 구분한다.

실제 TCP의 GET 간 간격은 약 1.010초였다. 1초 안내의 경우 POST→GET→GET→POST로 확인 완료했고, 60초 안내는 5초 예산 안에서 기다릴 수 없으므로 POST→GET 뒤 EXHAUSTED/deadline으로 끝났다. 조기 재요청이나 기한 연장은 없었다.

## 첫 클러스터 실행에서 드러난 별도 결함

수정 전 제품 이미지 `bf94bd18…`의 기준 경로는 `operations.restore_test` FAIL로 `FAILBACK_REQUIRED / CONTRACT_BREACH`에 머물렀다. 경로 효과는 confirmed_applied였지만 완료 대기 90초가 지나 전체 기능 시험은 실패했다. 해당 실행은 최종 SQL reconciliation이 완료된 비교 표본으로 사용하지 않는다.

기존 restore probe는 테이블별 READ COMMITTED 복사 후 현재 target을 새로 읽어 비교했다. `f5ce4f3`의 통제된 실제 DB 시험에서는 첫 COPY 뒤 주문·작업·결과를 같은 트랜잭션으로 커밋했을 때, live 51·51·51행에 비해 복원본이 50·51·51행으로 섞였다. probe가 FAIL이 되는 시점 경합을 재현했다. 원 클러스터 실행의 테이블별 원문까지 남은 것은 아니므로 모든 내부 사건이 같다고 단정하지 않는다.

`edcb952`에서 같은 read-only repeatable-read snapshot으로 digest·COPY를 수행하고 scratch 쓰기 트랜잭션 안에서 비교하도록 고쳤다. 원본·목적지를 scratch로 받지 않는다. 이후 `faa8897`에서 실제 `current_database()`가 target으로 연결되는 별칭도 TRUNCATE 전에 거부하도록 보완했다. 승인·fencing·게이트의 필수 검사·실패 조건은 바꾸지 않았다.

## 회귀 저장소 부족도 실패로 보존

첫 수정 회귀 9건 묶음은 동시성 시험을 포함해 8건 통과했으나 마지막 DB 생성 중 `pg_wal`의 DiskFull로 setup 오류 1건이 났다. 시계 관측도 periodic·stop에서 OperationalError/connect로 실패했다. 개별 시험 통과와 실행 전체 실패를 분리해 남겼다. 이 기록을 원인이 불명확했던 더 과거의 시계 실패에 소급하지 않는다.

다수의 작은 시험 DB가 runner 종료 때까지 남는 점에 맞춰 restore suite만 기존 worker/startup과 같은 1GiB tmpfs·1.5GiB 메모리 상한을 사용하게 했다. 공유 DB를 비우거나 요청·연결·재시도·복구 시간 제한을 늘리지 않았다. 이후 10건 모두 통과했고, 전용 저장소 사용은 452,340KiB였다. 실제 신규 쓰기를 포함한 live target은 51행, 복원본은 모든 테이블이 기준 스냅샷 50행으로 일치했다. 실제 변조 trigger의 금액 변경은 FAIL이었고, 기존 이전·복귀·초과 예산·출발지 독립성과 행 순서 회귀도 통과했다.

## 실제 비교 결과와 해석

두 최종 실행은 같은 하네스 `0742cd41c3f5745f640deaf04f9487163ec8d6ae`와 새 제품 이미지를 사용했다.

| 경우 | 최초 실패 / 100건 | 호출 내 결과 | 소진 사유 | 최대 호출 시간 | 최종 SQL / 최대 부하 완료 |
|---|---:|---|---|---:|---|
| 기준 v3·조회 안내 없음 | 3 (503 2·통신 1) | CONFIRMED 99·EXHAUSTED 1 | 8회 횟수 한도 | 2,709.638ms | 103/103 · 26,392.562ms |
| 후보 v4·조회 안내 1초 | 1 (503 1) | CONFIRMED 99·EXHAUSTED 1 | deadline | 4,410.581ms | 103/103 · 25,973.410ms |

**완료 한도 소진은 두 경우 모두 1건이다.** 후보는 남은 약 0.59초 안에 다음 1초 안내를 지킬 수 없어 기한을 늘리거나 일찍 요청하지 않고 중단했다. 5초를 모두 소비하기 전 EXHAUSTED를 반환할 수 있다. 후보가 100건 모두 기한 안에 성공했다거나 최초 503이 사라졌다고 쓰지 않는다.

조회 503 관측은 기준에서 7회·안내 없음, 후보에서 4회·모두 실제 응답의 1초 안내였다. 각 경우의 후속 부하 종료 복구 2회와 별도 target 확인 주문 3건은 최초 성공에 섞지 않는다. target의 최초 부하/호출 내 재시도 응답도 확인했다. 경로 PATCH는 각 1회, recovery event와 늦은 target 활성화는 0회, 원래 주문 50건·Secret GET 403·권한 없는 Pod 관측 403→unknown·잘못된 CA/호스트명 거부를 유지했다.

ClockWatch는 기준 232회·후보 267회 모두 통과했다. 실제 SQL·권한·소스 대조까지 각 실행은 완료됐으나 `completion_budget_satisfied=false`, `service_continuity=NOT_QUALIFIED`다. 합성 게이트의 availability pass로 실제 클라이언트 소진을 덮어쓰지 않는다.

단일 closed-loop 클라이언트라 대기 정책에 따라 도착 시각이 달라진다. 조회 수와 최초 오류 차이를 통계적 개선율로 해석하지 않는다. 응답 backpressure는 확인됐지만 **5초 완료 목표의 해결책으로는 부족하다**. 다음 경계는 쓰기 봉쇄→검증→활성화→경로 반영의 실제 지연을 분해하고, 그 결과에 따라 앱의 대기·내구성·취소·멱등성 계약과 전환 경로를 검토하는 것이다. 횟수·기한을 임의로 늘리거나 EXHAUSTED를 202/성공으로 바꾸지 않는다.

다음 측정은 효과 원장의 실제 단계 시각과 클라이언트 원장의 monotonic 완료 시간을 연결해야 한다. 사전 준비로 옮길 수 있는 작업과 writer 봉쇄 뒤에 반드시 수행할 검증을 구분하되, 게이트를 빼거나 증거를 앞당겨 재사용하지 않는다. 내구성 대기를 추가한다면 접수·커밋 완료·취소·만료·응답 유실을 각각 정의하고 기존의 "확인된 주문" 의미를 유지해야 한다. 일단 5초 기준은 바꾸지 않는다.

## 증거와 남은 범위

원문·키를 제외한 안전한 요약·원문 해시는 `local-dev-records/lookup-backpressure-20261119`와 공개 증거 문서에 연결한다. 첫 드라이버 분류 시험 실패, 최초 워커 복원 실패, 수정 전 동시성 실패, 저장소 부족 실행을 모두 유지한다. 공유 자원·AWS·팀 환경을 사용하지 않고 UUID kind·전용 TLS DB·네트워크만 실행별로 만든다. 실행 중 `caffeinate -di`를 사용했으며 OS 설정은 바꾸지 않았다.

안전한 원문 파일 74개의 해시를 연결했고, 모든 실행이 만든 전용 컨테이너·네트워크 이름 22개가 없음을 별도 읽기 전용으로 확인했다. 재현용 로컬 이미지는 보존했다. 원문 해시는 공개 배포나 서명된 운영 증명을 대신하지 않는다.

대상은 단일 로컬 arm64 kind 노드와 전용 PG 서버의 별도 DB다. 계획·IdP·일부 게이트 증거·로컬 witness·공유 fixture 인증서의 한계는 남는다. Ready·HANDOFF_COMPLETE·합성 availability PASS를 실제 클라이언트의 오류 없는 완료로 해석하지 않는다. 실운영 AWS→독립 온프렘, 장기 연결, 영속 백업·WAL/PITR, 고객 인증·부하 SLO·금융 보안 인증·서버 측 내구성 쓰기 대기는 별도다.
