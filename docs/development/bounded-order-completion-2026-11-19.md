# 목적지 사전 준비·한도 있는 완료 개발 기록

2026-11-19 · 개인 `feature/migration-request-qualification`.

## 범위와 선택

시작 SHA는 `e0c7acd4c2b51e1cadef630dd2b34fe75dd2e9fa`다. 다른 개인 작업 트리는 `d664566`에서 깨끗한 상태였고, 수정은 qualification 클라이언트와 이미 소유한 시험 경로에 한정했다. worker·quiescence·adapter·domain·스키마·팀 저장소·공유 클러스터·AWS는 변경하지 않았다.

서버 쓰기 큐를 급히 추가하는 대신, 먼저 준비 지연과 명시적 클라이언트 완료 정책을 분리했다. 새 정책은 기존 동기 클라이언트를 자동으로 바꾸지 않는다. 권한 거부·실패 영수증·알 수 없는 커밋을 성공으로 처리하지 않는 별도 opt-in 클라이언트다.

## 실패·관측 문제 보존

초기 `prepared-deferred` 실행에서는 실제 복구가 끝났지만 시험이 404만 기대해 실패했다. 제품은 이미 종료된 Pod의 terminal phase도 허용하며, 이 경우 API는 200을 반환할 수 있다. 실제 runtime 정지와 살아 있는 소유자의 거부는 계속 필수로 유지했다.

이를 기록하려고 추가한 첫 `kubectl` watch 명령에는 현재 버전이 지원하지 않는 옵션이 있어 종료 이력이 비었다. 해당 실패도 보존했다. 수정한 하네스는 지원되는 API watch에 resourceVersion을 전달하고, **이벤트 종류·Pod UID·phase·resourceVersion·관측 시각만** 저장한다. Pod 명세·Secret 본문·토큰을 남기지 않는다. watch stderr도 비공개로 보존해 수집 실패를 숨기지 않는다.

404가 없으면 아무 200이나 정지로 간주하지 않는다. 실제 terminal watch와 CRI 정지, 같은 SA/Pod에 결속된 감사 조회, 실제 successor의 recovery 기록을 함께 검사한다. 이전 워커가 Running인 상태에서 lease만 만료된 경우는 여전히 복구 0건이어야 한다.

`verified-prepared` 실행은 진행 중이어야 할 효과가 `unknown`으로 남아 실패했다. 근본 원인은 미확정이다. 재실행 성공으로 이 실패를 지우거나 운영 자격을 발급하지 않는다. `565a386`은 신원·권한 확인을 작업 접수 전에 마치고 접수 직후 효과 중단을 관측하도록 시험 순서를 정리했다.

`accepted-cold`에서는 100건이 이미 끝난 뒤 새 요청 없이 목적지 응답을 기다려 시간 초과했다. `8bb70ff`는 부하 시작을 실제 워커·권한 확인 뒤로 옮기고, 전환 뒤 확인 요청 3건을 별도 phase로 기록한다. 최초 100건의 오류와 추가 확인 성공을 혼합하지 않는다.

기존 bounded fixture의 “전부 기한 내 완료” 기대도 제품 안전성 검증과 분리했다. 기한 내 완료 여부와 EXHAUSTED 수를 직접 공개하며, 후속 복구로 이를 PASS로 바꾸지 않는다. 제품의 권한·fencing·효과 상태 전이에는 변경이 없다.

`measured-prepared`는 실제 successor 정지 확인 뒤 상태 조회에서 HTTP 422 `Authority store does not hold the latest witnessed record`로 실패했다. 이 응답을 재시도로 감추거나 통과로 해석하지 않았다. 코드상 DB 행을 읽은 뒤 외부 witness를 비교하고, 전이는 witness append 뒤 DB transaction을 commit한다. 동시 전이 구간의 관측 불일치 가능성이 있으나 이 실행의 원인으로 입증한 것은 아니다. 별도 원인 재현과 안전성 검토가 필요하다.

`3d724ba`는 401·403 등 거부 상태의 헤더를 받으면 오류 본문을 기다리지 않도록 수정했다. 기존 코드에서는 오류 본문 정지가 통신 오류로 정규화되어 추가 조회로 이어질 수 있었다. 읽을 수 없는 오류 본문 6종 회귀를 추가했으며, 새 고정 이미지에서 다시 측정한다.

## 검증 결과

제품 소스 `3d724ba`의 단위 92건과 실제 loopback TCP 시험 2건, 총 **94건 통과**를 확인했다. 중간 실행 84·85·86·87·88건 결과는 이 수에 더하지 않는다. TCP 응답 유실 시험은 RAM 상태를 가진 fixture이며 SQL 커밋 응답 유실 시험으로 확대 해석하지 않는다. SQL 데이터 보존은 별도의 실제 Pod·DB 대조로 판정한다.

실제 비교 기준은 제품 `3d724ba`, 하네스 `7ce0b4c`, 이미지 `sha256:b99f136eb590d2df900f3ea2bdddb5df244031315917aed6fbc71907cd331bf7`다.

- `final-cmp-cold`: 최초 오류 37/100. 복구 후 조회 HTTP 500으로 실패. 별도로 `clock_sample_failed` 1건이 있어 clock 검증도 실패다. 실제 clock skew가 한도를 넘었다고 추정하지 않으며, 표본 수집 실패 자체를 실패로 남긴다.
- `final-cmp-prepared`: 최초 오류 18/100(503 13·통신 오류 5). 최종 대조 103/103, 미해결·미완료 시도 0, 과거 주문 50, route PATCH 1회. 최대 부하 주문 완료 23,067.782ms.
- `final-cmp-bounded`: 최초 오류 5/100. client-local 결과 CONFIRMED 97·EXHAUSTED 3, 최대 inline 5,128.575ms. 실제 successor의 HANDOFF_COMPLETE가 90초 안에 확인되지 않아 통합 실패. 최종 SQL 관측은 실행되지 않았다. client는 120초 상한으로 종료됐고 `stop_received=false`이므로 이후 복구/확인 시도를 실제 전환 완료로 해석할 수 없다.

위에서 최초 오류 5건만 보이고 성공이라고 말하면 소진 3건과 제어면 통합 실패를 숨기게 된다. 세 경우의 오류 수를 일반적인 개선율이나 가용성 수치로 사용하지 않는다. 원인 미확정 500·422·effect unknown·최종 완료 시간 초과는 모두 별도 실패로 보존했다.

`a0d087b`는 시간 상한 종료를 부모의 검증 완료 신호로 취급하지 않도록 사후 하네스를 수정했다. 부모 신호가 없으면 client 결과만 기록하고 1로 종료하며 후속 재전송·확인 요청은 보내지 않는다. 이 변경 후 3종 클러스터 비교는 재실행하지 않았다. 실패를 반복 실행해 덮거나 새로운 성공 증거로 소급 적용하지 않는다.

기록·예비 실행을 포함한 UUID 컨테이너/네트워크 44개 이름의 부재를 확인했으며 공유 클러스터는 건드리지 않았다. 원문과 해시는 공개 증거에서 연결한다. 중간 후보와 최종 세 경우의 결과는 구분한다. 무중단·성능 SLO 또는 금융 보안 자격을 이 기록으로 발급하지 않는다.

## 해석과 다음 경계

사전 준비는 HTTPS health와 프로세스 준비이며 쓰기 활성화 승인이 아니다. source의 실제 연결 성공을 양성 대조로 두고, target INSERT가 SQLSTATE 42501로 거부됨을 확인한 뒤 이전을 진행한다.

최초 실패율, 모든 HTTP 시도, 부하 중의 논리 완료, 부하 종료 후 복구를 따로 기록한다. 재시도 대기 동안 closed-loop client는 새 주문을 내지 않으므로 경우별 실제 도착률이 달라진다. 각 경우 한 번의 실행으로 일반적인 개선율·무중단·운영 SLO를 선언하지 않는다.

다음 조사 우선순위는 관측 도중의 authority/witness 불일치 재현이다. DB 전이가 commit하기 전 외부 witness만 앞서는 구간과 실제 DB rollback을 같은 실패로 취급하는지, 통제된 트랜잭션 시험으로 구분해야 한다. 단순 422 무시·반복 성공만 기다리기·witness 덮어쓰기로 해결하지 않는다. 읽기 잠금 또는 일관된 revision 관측을 검토하더라도 실제 rollback 탐지 회귀가 함께 필요하다. 이번 작업에서는 제품 authority adapter를 수정하지 않았다.

그 다음 필요한 것은 일반 앱·게이트웨이의 운영 연결, 서버 측 쓰기 대기와 내구성·취소 의미, 고객이 승인한 완료 지연/오류/부하 기준, 실제 AWS→독립 온프렘 인수다. 기존 fixture 신원·공유 DB 인증서·파일 witness·단일 node/server의 제한도 남는다.
