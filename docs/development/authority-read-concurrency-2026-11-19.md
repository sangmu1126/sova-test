# 복구 조회 동시성 개발 기록

## 범위

다른 개인 작업 트리는 `e51b6a2`에서 깨끗했으며, 이후 변경과 authority/file witness 경로가 겹치지 않음을 확인했다. 이는 로컬 관측이며 다른 세션의 소유권 확인 응답은 아니다. 이번 범위는 authority adapter의 읽기·전이 동기화, 로컬 witness의 프로세스 잠금, 전용 시험·진단이다. 팀 저장소·공유 인프라·클라우드·스키마·도메인 상태 전이는 변경하지 않는다.

## 재현과 선택

`96f4ada`의 실제 DB 시험에서 기존 행과 최초 생성 행 두 경우 모두, 미커밋 SQL 행과 앞선 외부 증인을 대조하는 경합을 재현했다. 첫 실행은 총 13건 중 2건 실패다. 파일 backend에서는 별도 프로세스의 체인 분기·부분 줄 읽기·손상 자료형 처리도 재현했고 6건 중 5건이 실패했다. 이 실패를 후속 성공으로 대체하지 않는다.

조회에서 422/500을 무시하거나 반복 성공만 기다리는 방식은 선택하지 않았다. 단순 SQL 행 잠금은 최초 생성의 부재를 보호하지 못하므로 unit 범위의 transaction advisory lock을 사용했다. 파일은 전역 Python 객체 공유 대신 OS가 제공하는 프로세스 간 파일 잠금을 사용한다. 새 실행 조정 도구나 합의 프로토콜은 추가하지 않았다.

`after-canonical`은 실제 DB 15건 통과, 파일 및 기존 witness 회귀는 9건 통과다. 진단 추가 시 23건, 복귀·보안 보류·감사 보존 확장 후 **36건 통과**를 확인했다. 이들은 겹치는 회귀를 포함하므로 합산하지 않는다. 각 실행은 별도의 TLS DB에서 수행했고 DB·네트워크를 정리했다.

고정 제품 소스는 `0abcadcb4b8ab9426c747dbee39305c90d8916c7`, 보안 생산자는 `27e6e85514a7cbb3e43d216464b72d9bd78f3fcf`다. 로컬 arm64 이미지 `sha256:bf94bd18080210a11900913116adf4de144e84a538fbbc25d9b101640574633a`에서 Sova 318개·security 122개 설치 파일과 entrypoint가 일치했다. 이는 서명·SBOM·취약점 검사 또는 릴리스 자격을 뜻하지 않는다.

## 실제 Pod 재실행과 남은 일

첫 재실행은 `9c7918a` 기준이다. 사전 준비·부하 후 복구와 사전 준비·제한 재시도 두 경로가 실제 Pod·HTTPS·최종 SQL 대조까지 완료됐다. 후속 기동은 “lease 만료 후 실제 live-Pod 감사 조회 없음”으로 실패했다. 정리 시 수집한 워커 로그에는 이후 200 응답이 남아 있었다. 2초 고정 sleep만으로 감사 관측의 도착을 가정한 시험 경합을 발견했다.

`04eeac0`는 실제 인증 감사 증거를 최대 15초 동안 기다리고, 관측 뒤에도 같은 소유자·만료 lease·in_flight 효과·복구 0건·Running 상태를 다시 확인한다. 증거가 없는데 통과시키거나 판정 조건을 삭제하지 않았다.

최종 세 실행은 같은 하네스 `04eeac02acdf66cdc97837b8b792be371d94741c`와 제품 이미지로 수행했다.

- `accepted-cold`: 업무 부하 시작 전 source DB 연결의 `ConnectionTimeout`. 시험 fixture의 connect_timeout=2초를 넘겼다. 이 경우는 실행하지 않은 업무 요청을 오류 0건으로 보고하지 않는다. 제한을 바꾸거나 다른 세션 자원을 종료하지 않았다.
- `accepted-prepared`: 실제 HANDOFF_COMPLETE, 100건 최초 오류 23건, 후속 확인 3건 포함 독립 SQL 103/103. 기존 주문 50건, route PATCH 1회. 최대 부하 주문 완료 20,382.512ms.
- `accepted-bounded`: 실제 HANDOFF_COMPLETE, 100건 최초 오류 2건. 호출 내 CONFIRMED 98·EXHAUSTED 2이며 둘 다 8회 횟수 한도다. 부하 후 별도 조회·재전송 뒤 SQL 103/103. 최대 호출 내 시간 3,159.966ms, 후속 복구 포함 최대 완료 28,425.734ms. 이 실행은 완료 한도 전체 충족이 아니다.

최종 두 완료 실행의 원본/대상 권한·TLS 대조·실제 worker/SA/image 신원·살아 있는 소유자 복구 거부·정상 Pod 삭제 후 실제 복구가 통과했다. 상태 조회에 새 500·422가 관측되지 않았다는 결과는 이번 실행 범위에만 적용한다. 과거 모든 500·완료 시간 초과의 단일 원인을 확정하거나 운영 가용성을 보장하지 않는다.

정리 확인은 이번 재현·회귀·Pod 실행의 컨테이너·네트워크 이름 34개를 대상으로 했고 모두 없었다. 고정 이미지는 재현용으로 보존했다. `3b988cd`는 최종 측정 후 사용하지 않는 time import만 정리한 커밋이며, 동작·기한·판정 조건의 변경은 없다. Ruff와 문서·증거 검사는 최종 트리에서 확인한다.

다음 경계는 후속 기동 경로의 bootstrap DB 연결 실패 조사와 재현 가능한 실행 자원 조건 확보다. 운영 측 한도·오류 예산·부하를 정하고, 미완료 경로와 소진 호출을 별도로 검증해야 한다. 이 기록에서는 무중단·금융 보안 자격이나 실행 승인을 발급하지 않는다.
