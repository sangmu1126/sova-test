# 하드 링크 보존과 agent 공유 (2026-11-19)

남은 후보 두 가지를 사용자가 정한 순서(하드 링크 → agent 공유)로 진행했다. 결함은 [결함 목록](defect-register.md)에, 기능 설명은 [구현 안내](../contract-foundation.md)의 볼륨 절에 있다.

## 1. 하드 링크 보존 (#39)

**문제.** 링크 수가 2 이상인 파일은 경로마다 따로 복사돼 목적지에서 링크 관계가 사라졌다. 매니페스트는 경로와 내용만 비교하므로 인계는 "같음"으로 통과했다. 틀린 결과가 검증을 통과하는 문제라 먼저 했다.

**설계.**

- agent의 매니페스트에 `links`를 더했다. 같은 inode를 가리키는 트리 안 경로들의 묶음이다(묶음과 경로 모두 정렬).
  - 볼륨 밖과 이어진 링크는 묶음에 넣지 않는다. 볼륨의 것이 아니다.
  - 심볼릭 링크에 건 하드 링크는 "지원하지 않음"으로 보고한다. 복사가 확정되지 않으므로 조용히 틀리지 않는다.
- 복사(`sync_trees`)는 묶음마다 첫 경로에만 내용을 쓴다. 나머지 경로는 agent의 새 `/link`로 그 파일에 링크한다.
  - `/link`는 임시 이름(`.sova-link-…`)에 링크한 뒤 rename으로 바꿔 끼운다. 경로는 언제나 온전한 파일을 가리킨다. 이미 같은 파일이면 아무것도 하지 않는다. 디렉터리나 심볼릭 링크에는 링크하지 않는다.
  - 목적지 파일이 원본 묶음 밖의 경로와 파일을 나누고 있으면 그 파일을 새로 써서 끊는다.
  - 서비스 중 복사에서 묶음의 첫 파일이 바뀌면 그 묶음의 다른 경로도 마지막 복사로 미룬다.
- 비교는 항목과 링크를 함께 본다(`same_tree`). 차이에는 경로마다 양쪽의 링크 묶음이 나온다. 링크가 없는 트리의 manifest digest는 전과 같다.
- probe: 내용 비교는 보호 집합 안의 링크 묶음을 비교한다. 집합 안 파일이 집합 밖과 링크된 것도 보인다(한 경로짜리 묶음). 쓰기 거부의 "트리가 바뀌지 않음"과 복원 훈련도 링크를 포함한다.

단순 거부는 하지 않았다. Maildir처럼 배달 중에만 잠깐 링크를 거는 앱이 있어, 서비스 중 복사에서 거부하면 그런 앱은 옮길 수 없다.

**검증.**

- 단위 시험 6건. 실제 agent 프로그램을 임시 디렉터리에서 돌린다. 복사 뒤 목적지의 inode를 `os.stat`으로 따로 재서, 매니페스트와 별개로 확인한다.
- 결함 주입 4건을 모두 잡았다. 링크를 만들지 않음(3건 실패), 원본에 없는 목적지 링크를 둠(1건), 링크를 기록하지 않음(4건), 비교가 링크를 무시함(1건).
- kind 통합 시험 1건. 원본 볼륨에 시험 Pod로 git 객체 저장소 모양(세 경로)과 Maildir 모양(두 경로)의 링크를 만들고 복사했다.
  - 목적지를 읽기 전용으로 붙인 시험 Pod가 inode와 링크 수를 직접 쟀다. 세 경로는 한 inode, 링크 수 3이었다.
  - probe의 내용 비교(두 보호 집합)와 복원 훈련이 통과했다.
  - 목적지의 `pack`을 같은 바이트·mode의 별개 파일로 바꾸자 readback이 UNKNOWN이 됐다. 차이에는 세 경로가 모두 나왔다. 링크 하나가 빠지면 세 경로 모두 묶음이 바뀌기 때문이다(처음에는 시험이 한 경로만 기대해 실패했고, 기대를 고쳤다). probe의 `pack` 내용 비교도 실패했다. 다시 복사하니 APPLIED로 돌아왔다.
- 볼륨 관련 통합 시험 34건(probe, adapter, port-forward, control plane, 애플리케이션 단위, 클러스터 간)을 kind에서 돌렸다. 위 기대값 하나 말고는 모두 통과했다.

## 2. 실행 안의 읽기 agent 재사용 (#40)

**문제.** 관리형 클러스터에서 쓰기 정지가 75~105초로 kind의 3~5배였다. 정지 구간의 단계·readback·probe마다 agent Pod를 새로 띄우고 지운다. kind에서는 한 번에 약 0.9초지만, 관리형 클러스터에서는 스케줄링, 볼륨 연결, 이 기기와의 왕복이 더해진다.

**설계.** 워커의 한 실행(`Execution`)이 수명의 단위다. 워커는 한 실행으로 이어지는 단계들을 차례로 돌고, 끝나거나 막히거나 한 단계가 실패하면 `_run`을 빠져나온다. 그때 `Execution.close`를 부른다.

- `VolumeAgents(keep=True)`: 읽기 agent를 지우지 않고 같은 claim의 다음 사용에 다시 쓴다.
  - 자기가 띄운 agent만 다시 쓴다(메모리의 목록). 클러스터에서 찾아 쓰지 않는다. 그래서 키 없이 만든 가짜 agent를 쓸 여지가 없다.
  - 쓰기 agent, ReadWriteOncePod claim의 agent, 실패한 호출이 쓴 agent는 남기지 않는다.
  - 다시 쓰기 전에 Pod가 아직 도는지 본다. 유휴 종료까지 1분이 안 남았으면 새로 띄운다.
  - `release()`가 남긴 것을 모두 지운다.
- adapter(`keep_agents`)와 probe는 각자의 `VolumeAgents`를 쓴다. 서로의 agent는 쓰지 않는다.
- 활성화 직전, 목적지 claim을 마운트한 agent를 모두 지운다(`remove_agents`, 라벨과 무관). 단일 노드 볼륨을 다른 노드의 agent가 잡고 있으면 앱이 그 볼륨을 붙이지 못한다.
- 워커: `Execution`에 `close`를 더했다. `_run`의 `finally`에서 부른다. 한 단계가 실행을 만든 직후 실패해도 닫는다(만든 실행을 목록으로 넘겨받음). 복구 경로의 readback 뒤에도 닫는다. 닫다가 난 오류는 기록만 하고, 단계의 결과를 덮지 않는다. composite는 구성 요소마다 닫는다.
- agent: 인증된 요청이 `SOVA_AGENT_IDLE_SECONDS`(기본 600초) 동안 없고 처리 중인 요청도 없으면 스스로 끝난다. kubelet의 `/healthz` 확인은 시간을 늘리지 않는다. 끝난 Pod는 같은 단위의 다음 agent가 지운다. 워커가 죽은 경우의 안전망이다.

**검증.**

- 단위 시험 19건.
  - 보관 모드 11건: 가짜 클러스터로 만들고 지운 것을 기록한다.
  - agent 유휴 종료 3건: 실제 프로세스로 돌린다. 본문을 3초에 걸쳐 보내는 요청 중에는 끝나지 않는지도 본다.
  - 워커 실행 종료 5건: 끝까지 진행, 실행을 만든 단계의 실패, 나중 단계의 실패, 닫기 실패, composite.
- 결함 주입 9건(보관 7, 워커 2)을 모두 잡았다. 처음에는 "처리 중인 요청을 세지 않음"을 잡지 못해 시험을 더했다.
- kind 시험 1건. 같은 adapter로 단계를 진행하며 다음을 확인했다.
  - 쓰기 agent는 남지 않는다. readback 두 번이 읽기 agent 하나를 같이 쓴다.
  - probe의 agent는 따로 남는다.
  - 활성화가 목적지 claim의 agent(adapter·probe)를 모두 지운다.
  - 정리 뒤 남은 것이 없다.
  - 활성화 정리를 뺀 결함 주입을 이 시험이 잡았다.
- kind 통제 평면 시험(워커 경로) 5건을 여러 번 돌렸다. 정지 구간에서 새로 띄운 agent는 offline-copy 14→6, snapshot-cdc 12→3이었다. 쓰기 정지는 표와 같다(구현 안내). offline-copy 4회 중 1회는 37.3초였다. 원인은 재사용과 무관한 복사 단계의 지연이다(300KB 복사에 12.7초, 늘 새 agent를 띄우는 단계).
- 처음 측정에서 재사용이 덜 일어났다. 재사용 판정이 kubelet의 Ready 표시만 봐서, 막 띄워 응답하는 agent를 지우고 다시 띄웠다. 시작 때와 같은 기준으로 고쳤다.

## 4. 관리형 클러스터 실측 (EKS·GKE)

사용자 승인을 받아 AWS·GCP를 3시간 임대로 켰다(실행 4aa22c, 06:26~). EKS 1.37(t3.medium 한 대)과 GKE Autopilot에 Envoy Gateway를 설치하고, 통제 평면 시험(볼륨 3건, 애플리케이션)을 단계별 시간 기록과 함께 돌렸다. control plane의 DB는 로컬 시험 환경 것이다.

**시험 먼저 고침(T22, 6115de1).** #37 뒤로 GKE의 준비 단계는 Service 경로를 거부한다. 그런데 애플리케이션 시험은 게임을 Service 경로로만 넘겨 GKE에서 통과할 수 없었다.
- 게임 진입점을 Service·Gateway로 나눠 변형 4개(전략 2 × 경로 2)로 만들었다.
- `SOVA_TEST_ROUTE_FLOWS=dropped`면 Service 변형은 무거운 준비 없이 건너뛴다.
- kind에서 4건이 모두 통과했다(Gateway 경로 쓰기 정지 26.2초·15.7초, Service 경로와 비슷).

**1회차(EKS·GKE 동시).** GKE 5건 통과(Service 변형 2건 건너뜀). EKS는 6건 통과, 1건 실패였다.
- 실패한 것은 snapshot-cdc·Gateway 변형이다. 정지 전 복원 훈련의 scratch agent가 122초 동안 뜨지 못해 계약 위반(SAFE_HOLD)이 됐다.
- 같은 시험을 다시 돌리며 Pod를 3초마다 기록했다. 노드의 Pod 한도 17개가 찼고, 새 agent가 `Too many pods`로 Pending이었다.
- #40이 남겨 둔 읽기 agent가 자리를 차지한 것이다. 운영에서도 노드 한도, namespace의 Pod quota, 활성화 때의 앱 Pod에서 같은 일이 생길 수 있다(#41).

**#41 수정(5eee532).** `make_room(controls)`는 같은 클러스터에서 이 프로세스의 모든 `VolumeAgents`(adapter·probe)가 남긴 쉬는 agent를 지운다.
- 새 agent가 스케줄되지 못하면(Unschedulable) 한 번 make_room을 하고 마감까지 계속 기다린다.
- 생성이 403(Pod quota)으로 거부되면 make_room을 하고 한 번 더 만든다. 지울 것이 없거나 다른 거부면 그대로 실패한다.
- 활성화 직전에도 make_room을 한다. 쓰기 정지는 활성화에서 끝나므로 정지 시간에는 손해가 없다.
- 사용 중인 agent는 남긴 목록에서 빠져 있으므로 지워지지 않는다.
- 검증:
  - 단위 시험 5건을 더했다. 가짜 클러스터에 노드 자리와 quota를 두었다.
  - 결함 주입 5건을 모두 잡았다. 처음에는 "다른 거부에도 자리를 비움"을 놓쳤다. 시험이 agent를 남긴 `VolumeAgents`를 변수에 두지 않아 바로 GC되어 목록에서 빠졌기 때문이다. 시험을 고쳤다.
  - kind 통합 시험이 활성화 뒤 원본 claim의 남긴 agent도 사라졌는지 본다. 활성화의 make_room을 뺀 결함을 잡았다.
  - 단위 979건이 통과했다.

**2회차(EKS·GKE 동시, 수정 뒤).** EKS 7건, GKE 5건이 모두 통과했다. EKS에서 `Too many pods`로 Pending이 두 번 생겼지만 인계는 진행됐다.

**EKS만 돌린 회차.** 볼륨 3건을 두 번 돌리려 했다. 첫 회의 앞 두 건(55.7초, 32.7초)이 끝난 뒤 Mac이 잠들었다(08:01, 화면 켜 두기를 앞서 끈 탓). 깨어난 뒤 나머지는 EKS `Unauthorized`로 실패했다. 임대가 끝난 뒤(09:26) 자동 정리도 잠든 사이에 끝나지 못했다. 클러스터와 DB는 클라우드 쪽 예약 삭제로 지워졌다. 남은 역할·디스크·예약 등은 12:20에 `down`으로 지웠다. 스위치가 다시 조회해 "실행 4aa22c의 것은 AWS·GCP 어디에도 남지 않음"을 확인했다.

**결과(쓰기 정지).** 표는 [구현 안내의 "쓰기 정지의 구성"](../contract-foundation.md)에 있다.
- 볼륨 단위는 EKS에서 offline-copy 83.0초 → 43~56초, snapshot-cdc 76.1초 → 33초였다.
- GKE에서는 91.7초 → 62~73초, 74.7초 → 26~31초였다.
- Service 경로의 애플리케이션 단위는 EKS에서 100.5초 → 63초, 94.1초 → 50.5초였다.

**설명하지 못한 것.** EKS 2회차의 볼륨 snapshot-cdc(61.5초)에는 adapter·probe 호출이 없는 빈 구간이 있었다(쓰기 거부 probe 뒤 26초, 활성화 전 13초).
- 1회차와 EKS만 돌린 회차에서는 없었다. 그때 Mac은 깨어 있었다(전원 기록).
- 빈 구간에 스레드 스택을 남기는 계측을 더해 다시 돌렸지만 재현되지 않았다.
- 동시에 돈 GKE 세션과 로컬 DB에서 경합했을 가능성은 확인하지 못했다.

## 5. 17차 전체 회귀

#41 수정과 애플리케이션 시험 변경을 넣은 a3224b0에서 돌렸다. 평문 2004 통과, 0 실패, 1 오류, 302 건너뜀. TLS 55 통과.

- 오류는 `test_identity_unit_handoff`의 fixture가 Keycloak에 realm을 만들다 HTTP 시간 초과(15초)로 실패한 것이다.
- 실행 중 배터리가 1%가 되어 Mac이 저전력 잠자기에 들어갔다(14:12, 17:21에 깨어남). `caffeinate`는 배터리가 바닥나는 것을 막지 못한다. 시험 시간 113분도 그 영향이다.
- 전원에 연결한 뒤 그 시험 파일만 다시 돌려 2건 통과했다.
