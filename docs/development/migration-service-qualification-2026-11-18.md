## 선택 이유와 구현

기존 서비스에는 정방향 HTTP 계획·승인·실행 접수는 있었지만 복귀 계획의 HTTP 경로가 없었다. domain의 `compile_failback`, coordinator의 `require_failback`, 승인·claim·epoch·효과 원장이 이미 있으므로 이를 호출하는 얇은 서비스 경로를 추가했다.

1. 운영자의 제한된 복귀 사유 코드로 `FAILBACK_REQUIRED`를 요청한다. 반복 요청은 revision을 다시 올리지 않는다. 요청 자체는 쓰기를 열거나 승인하지 않는다.
2. planner가 현재 역방향 등록 자료와 원래 계획·현재 authority를 사용해 복귀 계획을 만든다. 내부 요청을 버전 `failback.v1`으로 보존한다.
3. 기존 독립 approver가 새 계획을 승인한다. admit은 저장된 요청을 다시 읽고 현재 자료로 재컴파일한다. 정방향 승인을 복귀 승인으로 간주하지 않는다.
4. 기존 `HandoffWorker.drive`와 PostgreSQL factory를 그대로 실행한다. 복귀에는 새 워커 객체를 사용한다. 배포된 운영 daemon이나 OS 재시작 시험이라고 표현하지 않는다.
5. fixture로 신뢰·수집 완료 시각을 준비하되, 등록·attest·계획·승인·실행 접수·복귀 요청·상태/관측 조회는 실제 loopback TCP HTTP로 호출한다.
6. 전환 전 주문, 차단 중 503, 목적지 신규 주문, 복귀 후 재시도와 신규 주문·조회 결과를 독립 요청 원장과 최종 DB로 대조한다.

테스트에서는 안정화 직전의 측정 콜백에 명시적인 Python 예외를 주입한다. 정방향은 `ROUTE_CONFIRMED`까지만 갔다가 복귀 필요 상태로 남는다. 이미 완료된 정방향 상태를 강제로 되돌리지 않는다. domain의 terminal·재복귀 금지 규칙을 유지했다.

## 증거와 운영 한계

[사용·범위 문서](../migration-service-qualification.md), [공개 가능한 실행 요약](../evidence/service-request-qualification-20261118.json)에 구현 접점·소스 지문·시험 결과를 연결한다. 원문은 비공개 로컬 `local-dev-records/migration-service-qualification-20261118/`에 있다. 공개 요약에는 JWT·DSN·개인 키·사용자 홈 경로를 넣지 않는다.

서비스·주문 HTTP는 loopback 평문, 신원은 생성한 시험 JWKS, 업무 DB는 한 서버의 논리 DB들, 경로는 메모리 Route, witness는 로컬 파일이다. 방향별 프로필·자격·인벤토리는 합성 fixture다. 실제 운영 등록·발행자 신뢰·최소 권한·네트워크·고객 데이터의 증거가 아니다.

운영 배포·독립 두 서버·실제 AWS→VM·외부 Edge·부하·프로세스 장애·독립 보존·자격 발급은 남아 있다. `service_continuity=NOT_QUALIFIED`, `qualification_issued=false`, `authorizes_execution=false`를 유지한다. 원격 CI나 금융 보안 인증 통과도 주장하지 않는다.
