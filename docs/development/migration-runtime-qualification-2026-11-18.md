# MQ-03 runtime 개발 기록

2026-11-18 · 개인 저장소 전용 브랜치. 팀 배포·정책·태스크는 변경하지 않는다.

## 기준과 범위

- 시작 기준: `f86bc08cc82514b162530ee861b222539882633d`.
- Security 생산자: `27e6e85514a7cbb3e43d216464b72d9bd78f3fcf`.
- 다른 세션의 관측 기준: `b24cd7cbabe537dfaa88509ff1bdcb79055adbbf`. 새 서비스 수정 경로 `main.py`·`auth.py`·기존 소유 `api.py`와 겹치지 않았다.
- 시험은 새 TLS PostgreSQL·loopback API·HTTPS JWKS만 사용한다. 공유 kind·AWS·팀 클러스터와 다른 작업 트리는 수정하지 않았다.
- 변경하지 않은 영역: domain·SQL 스키마·어댑터·워커·infra. 서비스 진입점과 기존 인증 실패 분류, 전용 시험만 확장했다.

## 선택

기존 `create_app` 테스트에 또 다른 mock을 붙이는 대신 실제 CLI 프로세스와 `ServiceConfig`·DSN 파일·HTTPS JWKS 조회를 통과시켰다. API 메모리와 키 캐시가 없어져도 승인 이후 실행 접수와 복귀 재컴파일이 가능한지 확인한다. 워커 배포까지 끝난 것으로 표현하지 않는다.

프로필의 engine 버전은 실제 source/target DB에서 읽고 qualification의 방향별 fingerprint를 갱신했다. 다른 합성 인벤토리·자격을 실제 발행 자료로 바꾸지는 않았다.

JWKS 인증서 검증 실패는 새 인증을 중단하고 503으로 응답한다. 클라이언트 응답에는 URL·CA 경로·외부 응답을 넣지 않는다. DB 인증서 실패는 기존 readiness의 503으로 확인한다. CA 참조 수정과 API 재시작 이후의 정상 동작을 각각 대조한다.

## 첫 실행의 실패와 조치

runtime run-01은 **70 PASS, 11 FAIL**이었다. 실패 실행의 원문·JUnit·시각 샘플·자원 정리 기록을 보존했다.

1. 8개 기존 서비스/워커 시험은 5ms 전으로 만든 수집 완료 시각이 DB 시각보다 미래라 거부됐다. 관측한 최대 시각 차이는 약 16.8ms였으며, 실행기 1초 환경 한도 안이어도 fixture의 5ms 가정을 만족하지 못했다. 제품의 미래 시각 거부 조건은 수정하지 않았다.
2. 이미 다른 세션의 `b24cd7c`가 이 fixture를 1초 전으로 고쳤다. 같은 수정 대신 해당 커밋을 이 브랜치에 cherry-pick했다(`5276245`). 원 작성 이력과 변경 이유를 보존했다. 함께 들어온 `valid_for` 선택 인자의 기본값은 4분이고, 이번 자격 시험에서는 늘리지 않았다.
3. 새 runtime 3개 시험은 API가 정상 종료 로그를 남긴 후 SIGTERM 코드로 끝나는 것을 비정상 종료로 오판했다. 코드 0 또는 SIGTERM에 더해 두 정상 종료 로그·강제 종료 없음까지 확인하도록 시험을 바꿨다. 제품의 신호 처리 코드는 변경하지 않았다.
