## 범위와 판단

기존 prepared v2는 목적지 프로세스를 미리 만들지만, 선택 라벨은 원 작업자 중단 뒤 활성화한다. 따라서 목적지 사전 준비·정상 전환과 작업자 장애를 분리해 관측할 필요가 있었다. v2의 실제 CRI pause·live owner 복구 거부·정상 삭제·후속 복구를 없애는 대신 v3 정상 경로를 추가했다.

다른 개인 작업 트리는 `e8c6652b0cb82ae1918fb838cb4133ae8c2e36ac`이며 Kafka compaction 시험과 별도 개발·결함 문서 경로만 최근 변경됐다. 경로 대조에서 겹침이 없었고 해당 작업 트리는 수정하지 않았다. `SESSION-SCOPES.json`은 범위 안내이며 다른 세션의 응답이나 잠금으로 간주하지 않는다.

v3는 접수 전에 target Pod·선택 라벨·Ready를 준비하지만 source Service는 원본만 선택한다. target 앱 INSERT는 실제 SQLSTATE `42501` 거부를 확인한다. 이후 실제 워커가 기존 승인·소유권·효과 절차를 실행한다. 별도의 타이머나 수동 라벨 전환으로 완료시키지 않는다. 정상 경로에는 owner pause·삭제를 주입하지 않고 복구 이벤트가 0건이어야 한다. 서비스 PATCH 1회의 실제 SA UID·Pod UID, 같은 target Pod의 최초 부하 중 업무 응답도 확인한다.

제품 소스·이미지·승인·fencing·복구 규칙·DB 연결 제한·재시도 횟수·완료 기한은 변경하지 않았다. `tests/` fixture와 실행 모드, v3 프로필만 추가했다. denied Pod 관측 도우미는 기존 실제 403→unknown 검사를 추출한 것으로, v2의 검사 시점과 거부 조건을 유지한다.

## 기존 장애·복구 대조의 환경 검증 실패

기존 `prepared_deferred`도 같은 하네스로 실행했다. 실제 CRI pause 뒤 lease가 만료돼도 Running owner의 복구 이벤트는 0건이었다. 정상 Pod 삭제 뒤 CRI 종료·실제 Pod 관측 200/404를 확인하고 후속 워커가 경로를 다시 바꾸지 않은 채 복구했다. 기능 시험 1건은 통과했고 최종 SQL 103/103·기존 주문 50건, 최초 실패 21건(503 16·통신 5), 최대 부하 주문 완료 23.212초였다.

그러나 **시계 감시 239개 기록 중 1회 DB 관측이 실패해 runner는 종료 코드 1**로 끝났다. 나머지 정상 관측에서 시차 하한은 1초 이내였으나 누락된 관측을 정상 시계로 가정하지 않는다. 예외 종류·원인을 구분할 정보가 해당 기록에는 없으므로 연결 시간 초과나 자원 경합으로 단정하지 않는다. 기능 통과만으로 환경 검증까지 통과 처리하지 않으며, 이번 장애 대조 실행 전체를 인수 성공으로 사용하지 않는다. 재실행으로 이 실패를 지우지 않았다.

정상 v3 두 실행의 시계 감시는 각각 183·208개 기록 모두 통과했다. 세 실행의 전용 컨테이너·네트워크 이름 12개를 별도 읽기 전용 조회로 확인했고 모두 없었다. 캐시 이미지는 재현용으로 보존했다.

## 회귀·운영 경계

최초 오류·조회·재시도·완료 후 확인의 구분을 지키는 지표 회귀 7건이 통과했다. 첫 직접 단위시험 호출은 고정 security 소스가 PYTHONPATH에 없어 수집 전에 중단됐다. 같은 고정 소스를 연결한 뒤 실행했으며 패키지 버전을 바꾸지 않았다. 실제 통합시험의 기존 Starlette deprecation warning도 숨기지 않았다.

각 실행은 별도의 UUID kind·전용 TLS DB·네트워크를 사용한다. `caffeinate -di`로 실행 중 시스템·화면 잠자기를 억제했으며 OS 설정은 바꾸지 않았다. AWS·팀 클러스터·사용자 kubeconfig를 사용하지 않는다. 이전 시간 초과·복구 오류·완료 한도 소진 기록도 삭제하지 않았다.
