# 관리형 Kubernetes 실측: 볼륨·세션·Gateway (2026-11-18)

사용자 승인으로 클라우드 스위치를 켜고(실행 ce27b0, 6시간 임대), EKS와 GKE Autopilot에서 kind의 Kubernetes 시험을 실측했다. 결과와 수치는 [구현 안내의 관리형 절](../contract-foundation.md#관리형-kubernetes-실측-eksgke-2026-11-15)에, 결함은 [결함 목록](defect-register.md) #35~#37과 T14~T19에 있다.

## 순서

1. 스위치가 EKS에 볼륨을 만들 수 없음을 확인하고 EBS CSI 드라이버를 넣었다. 처음 방식(노드 역할)은 컨트롤러가 자격을 얻지 못해 실패했다. IMDSv2가 한 홉만 답하기 때문이다. Pod Identity로 바꿨다. 이미 만든 애드온은 갱신을 받지 않아(CREATING), 연결을 직접 만들고 컨트롤러를 재시작했다. 연결 직후 만든 Pod에는 자격이 주입되지 않아 한 번 더 재시작했다. 이 동작을 스위치에 반영했다(재시작 뒤 자격 주입 확인).
2. Envoy Gateway: EKS에는 그대로 설치됐다. GKE는 Gateway API CRD를 직접 관리하고 표준 채널만 허용해, 클러스터의 CRD를 쓰는 옵션을 더했다.
3. 1회차: 게시판이 두 클러스터 모두에서 바로 실패했다. 블록 볼륨의 최상위가 root 소유라 `fsGroup`이 필요했다(T14). 중단했다.
4. 2회차: GKE에서 볼륨 인계가 모두 실패했다(HTTP 400). 거부 본문을 받으려고 일회용 플러그인을 붙였다. GKE Warden이 호스트 이름 노드 affinity를 거부한 것이었다. agent를 Pod affinity로 배치하게 고쳤다(#35). 중단했다.
5. 3회차: EKS 35/39, GKE 35/39.
   - 실패의 원인은 계획 만료(T15), watermark 여유(T16), 이 기기와 EKS 사이의 연결 끊김(#36), 세션 drain(#37)이었다.
   - #36과 T15·T16을 고친 뒤 실패한 시험만 다시 돌렸다. EKS는 39/39가 됐다.
   - GKE는 세션 시험 하나만 남았다.
6. 세션 시험의 증거를 보려고 readback마다 peer를 출력했다. 남은 연결은 경기 클라이언트의 세 연결이었다. 일회용 실험으로 확인하니, selector를 옮긴 지 7초 만에 경기 3개가 모두 시간 초과로 끝났다(#37). EKS(kube-proxy)와 GKE의 Gateway 경로에서는 정상이다.
7. EKS → GKE 볼륨 인계: 기능 시험 2건이 통과했다. 64MiB 복사는 프록시 46.3초, port-forward 62.5초였다.
8. 시험 namespace와 PV가 남지 않았음을 확인하고 `down`했다. 스위치가 다시 조회해 "실행 ce27b0의 것은 AWS·GCP 어디에도 남지 않음"을 확인했다(EKS·GKE 클러스터, 역할, DB, 예약, 디스크).

## 결정이 필요한 것

- #37의 해법. 후보는 세 가지다.
  - 재전송 증가로 끊김을 감지하고 경로를 즉시 되돌린다.
  - 운영자가 데이터플레인을 등록한다.
  - eBPF 데이터플레인에서는 Gateway 경로만 허용한다.
- 관리형 클러스터의 쓰기 정지(75~105초)를 줄이는 agent 공유. probe의 독립성 설계를 다시 봐야 한다.

## 그 뒤: #37을 "미리 측정"으로 (4fc4714)

사용자가 "미리 측정"을 골랐다. Service 경로 세션의 `stage_target`이 단위의 namespace에서 측정한다.
- 일회용 echo 서버 Pod, 그것을 고르는 Service, 연결 하나를 붙잡고 0.5초마다 한 줄씩 주고받는 클라이언트 Pod를 쓴다.
- selector를 Pod가 없는 쪽으로 옮기고 엔드포인트가 빠진 것을 확인한 뒤, 8초 동안 오류 없이 계속 오가야 한다.

kind에서 처음에는 클라이언트가 Service 규칙이 반영되기 전에 연결해 거부됐다. 첫 연결은 30초 안에서 다시 시도하게 했다. 그 뒤 경로를 옮긴 뒤 8초 동안 16번 오갔다. 판정 기준을 망가뜨린 결함 주입은 시험이 잡았다. 세션·애플리케이션·Gateway 세션 시험도 통과했다.

GKE에서 실제로 거부하는지 확인하려고 GCP만 다시 켜려 했으나, 자동 승인 검사가 거부했다. 사용자 승인을 기다렸다(아래 2026-11-19에 확인).

## 그 뒤: 13차 전체 회귀 (2026-11-19)

d664566 기준으로 kind 전체 회귀를 돌렸다. 1920 통과, 44 실패, 3 오류, 302 건너뜀(61분)이었다. 실패의 원인은 두 가지였다.

- **시험 환경(T20).** 자정을 넘긴 뒤 보안 패키지를 쓰는 시험 46건(실패 43, 오류 3)이 "모듈 없음"·"파일 없음"으로 실패했다.
  - 세션 작업 폴더에 git archive로 풀어 둔 원본은 수정 시각이 커밋 시각(11-07)이었다. 자정의 임시 파일 정리가 이를 오래된 파일로 보고 지웠다.
  - 패키지는 회귀 시작 때 이미 불러온 상태였다. 그래서 그 뒤에 처음 쓰는 하위 모듈부터 실패했다.
  - 같은 커밋에서 수정 시각을 지금으로 다시 풀었다. 실패한 시험 파일 12개(164건)를 다시 돌려 모두 통과했다.
- **제품(#38).** `test_absolute_deadline_stops_trickling_response`가 실패했다. 0.15초 마감의 GET이 1.96초 걸렸다.
  - #36에서 넣은 읽기 재시도가 원인이었다. 응답이 조금씩 흘러오다 자기 마감에 걸려 끊긴 경우도 연결 실패로 보고 세 번 읽었다(대기 0.5초 + 1초 포함).
  - 재시도는 응답 전의 실패에만 해당한다. 상태 줄을 받은 뒤의 실패는 최종으로 했다(ab5b5c2).
  - 단위 시험 2건을 더했다. 연결 대역 `_attempt`가 응답 없는 종료는 연결 실패로, 끊긴 응답은 최종 실패로 내는지 본다.

## 그 뒤: #37을 GKE에서 확인 (2026-11-19)

사용자 승인을 받아 GCP만 3시간 임대로 켰다(실행 85ac31, 00:44~01:18, 34분). GKE Autopilot에 Envoy Gateway를 설치하고 세션 시험을 `SOVA_TEST_ROUTE_FLOWS=dropped`로 돌렸다.

- **준비 단계 측정(통과).** 경로를 옮긴 뒤 클라이언트가 시간 초과(`TimeoutError`)로 끊겼다. 준비 단계는 "Gateway로 보내라"며 거부했고, readback은 UNKNOWN, 증거는 `survive: false`였다. 일회용 Pod·Service는 남지 않았다.
- **Gateway 세션 인계(통과).** 같은 클러스터에서 경기가 원본에서 끝나고 새 경기는 목적지로 갔다.
- **drain 상한(통과).** 준비 단계를 거치지 않는 시험이다.
- **Service 경로로 세션을 넘기는 시험과 원본 재시작 시험(건너뜀).** 둘 다 준비 단계를 거치므로 이 데이터플레인에서는 거부된다. 처음에는 원본 재시작 시험이 그 거부로 실패해, 이유를 밝히고 건너뛰게 했다.

처음 실행의 증거에는 `exchanges_after_move: -3`이 찍혔다. 클라이언트가 오류 줄에 그때까지 주고받은 횟수를 남기지 않아, 0에서 이동 전 3을 뺀 것이다. 오류 줄에도 횟수를 남기고 음수가 되지 않게 고쳤다. 다시 돌리니 `exchanges_after_move: 1`이었다. 이동 직후 한 번 오가고 끊겼다는 뜻이다.

`down` 뒤 스위치가 다시 조회해 "실행 85ac31의 것은 GCP에 남지 않음"을 확인했다.
