# 신뢰 grant 순환 차단 수정과 로컬 이전 회귀 복구

2026-11-21 개인 개발 기록. 기준 `7702e20d4fabea1bd21c8dace025b1225e5aa75d`. 팀 저장소·기존 개인 AWS·VM 배포 변경과 구분한다.

## 조사 결과와 변경 이유

이전 기록에서는 실패 14건을 신뢰 발행·snapshot의 준비 순서 문제로 보았다. 추가 조사에서 **snapshot 지문 → unit ID → 검증 scope → 권한 등록 → snapshot 재작성 요구**가 순환한다는 것을 확인했다. 따라서 준비 순서만 바꾸면 된다는 최초 진단은 이 결과로 보완한다.

수정은 [ADR-0009](../adr/0009-verifier-grants-and-implementation-impact.md)를 따른다. 정상적인 신규 키 등록과 다른 trust 항목이 모두 같은 scope 추가만 정책 변경으로 발행한다. scope 축소·회수·유효기간·검증 버전 변경과 실제 구현 변경은 기존 실행 차단을 유지한다. 기존 도메인 게이트를 통과시키기 위해 조건을 삭제하지 않았다.

- 새 owner migration은 29번째로 추가했다. 기존 28개 migration·기록된 이벤트는 바꾸지 않는다.
- 정책 변경 시 이전 PASS를 무효화하고 변경 뒤 새 검증을 요구한다. 현재 키 회수·범위·유효기간 확인은 기존 서명 검증 경로를 재사용한다.
- 모호한 문서나 row/scope 결속 오류를 권한 추가로 추정하지 않는다.

## 함께 드러난 시험 준비 문제

기존 차단을 해소하자, 최신 범주별 위치 관측자가 연결되지 않았던 오래된 시험 설정도 드러났다. 운영 코드의 `category_observer_unavailable` 거부는 유지했다.

로컬 시험에는 명시적인 `FixturePlacement`를 주입했다. 각 범주의 승인 위치는 고정된 합성 입력이며 실제 지리·백업 복사본·감사 저장소·AI 데이터 위치를 측정한 것이 아니다. unknown 범주와 허용하지 않은 위치는 실패하고, 일회용 control DB 신원을 확인하지 못하면 생성 자체를 거부한다. 공용 시험 실행기는 위치 observer가 없으면 계속 차단한다. 실제 AWS/RDS 시험에 이 fixture를 자동 주입하지 않는다.

일부 이전 fixture는 관측을 임의로 1초 앞당겨 작성하고 있었다. 새 정책 변경 이후에 검사했어도 이전 증거처럼 보이는 문제가 있어, 합성 증거의 시각은 실제 control DB에서 읽는다. 호스트가 그 시각에 도달하지 못하면 제한 시간 내 실패한다. 이벤트를 과거로 바꾸거나 만료를 늘리거나 시스템 시각을 수정하지 않는다.

기존 registry 손상 시험은 새 DB publication barrier에 의해 잘못된 head 저장 자체가 거부되는 상태였다. trigger를 끄지 않고, 올바른 tenant 문맥에서도 불변 이력 없는 head가 commit되지 않고 기존 revision이 보존되는지 확인하도록 바꿨다.

## 검증

최초 수정 실행의 실패도 보존한다. SQL JSONB 연산자 괄호, upgrade 시험의 열려 있는 transaction, 이후 드러난 fixture 위치·시각 문제를 고쳤다. 실패를 skip·재시도로 숨기지 않았다.

중간 실행에서는 기존 실패 15건을 포함한 서비스 시험 **134개가 모두 통과**했다. 최종 실행은 문서 결속 오류·실제 DB 인계·키 회수와 API 재시작 회귀까지 넓혀 **170개 통과, 실패·오류·제외 0**을 확인했다. 원래 실패한 15건을 모두 포함하며, 불변 이력 없는 head 저장 시험은 현재 DB가 저장 자체를 거부하는 더 강한 조건으로 변경했다. 최종 수치와 원본 지문은 [증거](../evidence/verifier-grant-recovery-20261121.json)에 기록한다.

확대 과정의 실패 실행도 보존했다. 일회용 DB의 384MiB 저장 공간이 가득 찬 실행은 성공에 합산하지 않았다. 이후 이 세션 소유 시험 컨테이너만 저장 공간 2GiB·메모리 상한 2.5GiB로 만들었고, 최종 저장 사용량은 54%였다. 다른 VM·컨테이너의 우선순위는 변경하지 않았다. 기존 TLS 음성 시험은 실제 TLS 시험 서버에 맞춰 잘못된 인증 신뢰와 평문 접속 거부를 각각 확인하도록 수정했다. 복구의 두 단계와 독립적인 권한 등록의 원인 기록도 실제 계약대로 검증했다.

직전 실행은 169개 통과·1개 실패였다. 해당 시험이 호스트 시각에서 5ms를 빼서 만든 snapshot을 DB가 미래 시각으로 거부했다. 시험 입력을 실제 DB에서 읽은 시각으로 고친 뒤 최종 170개를 다시 실행했다. 운영 DB의 미래 snapshot 거부나 시각 검증은 완화하지 않았으며, 이 수정으로 운영 환경의 시계 오차 문제까지 해결했다고 주장하지 않는다.

전체 Python 단위 시험은 **1,406개 통과, 제외 0**이다. 공급자 인덱스를 사용하지 않고 wheel을 만들고 새 migration의 바이트가 원본과 같음을 확인했다. 이 wheel은 운영에 설치·배포하지 않았다.

코드 커밋은 의미 분류 `dead87a`, 증거 시각 `083e44b`, 명시적 위치·TLS 시험 `5be4f17`, 불변 head 거부 `50395e7`, 확대 시험 자원 `b2a4b9a`, 복구·인과 기록 `0387391`, 재확인 snapshot 시각 `aa0a468`로 나눴다. 최종 시험 시작 시 HEAD는 `0387391`이었고, 실행한 파일들의 SHA-256이 `aa0a468`에 커밋된 바이트와 모두 일치하는지도 별도로 확인했다.

## 운영 경계

현재 검증은 일회용 로컬 PostgreSQL·HTTP/API·worker·서명/승인 경로다. 위치·인벤토리·검증 신뢰는 명시적인 시험 입력이다. 실제 업무 SQL 효과와 요청 결과 검증이 있어도 실제 AWS→VM 이전, 물리적 데이터 레지던시, 금융 규제 준수, 무중단 SLO를 입증한 것은 아니다.

개인 AWS 시험 창과 기존 TLS·역할의 기한을 연장하지 않았다. 실제 모델 호출·VM 우선순위 변경도 보류 상태를 유지한다. 실제 VM DB는 기존 schema 상태이며 새 migration을 자동 적용하지 않는다. 코드 지문이 바뀌었으므로 과거 방향별 C3 자격을 재사용하지 않는다.

11/21 00:25 KST 읽기 전용 점검에서는 개인 계정·소유 RunId와 출발지 EC2의 정지 상태를 확인했다. 개인 VM의 API 응답과 소유 namespace UID도 확인했다. 이는 접속 준비 상태이며 실제 워크로드 이전·데이터 무결성·새 C3 자격을 의미하지 않는다.

다음 운영 인수에는 새 유효 기한의 자격과 owner migration 적용, 현재 코드의 방향별 재검증, 같은 실제 앱·계획의 콘솔 연결이 필요하다. 원래 1–6 전체 완료로 보고하지 않는다.
