# 전환 중 결과 조회의 대기 안내

2026-11-19 · 개인 qualification 주문 API·시험 경로의 opt-in 정책.

## 발견한 문제

기존 시험 API는 주문 제출 POST가 불가능하면 `503 + Retry-After: 1`을 반환한다. 그러나 같은 업무 키의 결과 조회 GET이 불가능하면 대기 안내 없이 503만 반환했다. 기존 bounded 클라이언트는 안내가 없을 때 최대 0.5초 full jitter를 쓰므로, 전환이 끝나기 전에 조회를 반복해 총 8회 한도를 소진할 수 있다.

새 경로는 GET의 일시적 503에도 **기존 POST와 같은 1초 안내**를 준다. 클라이언트의 5초·8회·시도별 네트워크 1초, 멱등 키 조회 후 재제출, 인증 거부 중단 규칙은 바꾸지 않는다.

[RFC 9110 §10.2.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.3)은 Retry-After를 후속 요청 전 대기 안내로 정의하고, 503에서는 서비스의 예상 불가 시간을 나타낸다. 이 시험의 1초는 이미 POST에서 쓰는 backpressure 정책이다. 1초 뒤 실제 복구를 보장하거나 요청 기한을 연장하는 값이 아니다. 기존 클라이언트가 지원하는 형식은 delta-seconds이며 날짜 등 미지원 형식을 무시하지 않는다.

## 응답·권한 계약

| 관측 | 의미 | 다음 동작 |
|---|---|---|
| GET 503 + Retry-After 1 | 지금은 커밋 결과를 확인할 수 없음 | 같은 키의 조회를 안내 시간보다 일찍 보내지 않음 |
| GET 404 | 권한 있는 현재 DB 조회에서 해당 키가 없음 | 같은 키·내용의 제출 가능 |
| GET 200 + 맞는 영수증 | 해당 키의 결과 확인 | POST를 다시 보내지 않고 완료 |
| 401·403·409 등 | 인증·범위·업무 충돌 등의 최종 거부 | 일시 장애로 바꿔 재시도하지 않음 |
| 안내 시간이 남은 기한보다 김 | 기한 내 다음 시도 불가능 | 조기 요청·기한 연장 없이 EXHAUSTED |

503을 404로 바꾸거나 source 쓰기 차단을 풀지 않는다. 일시적 결과 조회 불가와 권위 있는 키 부재를 구분한다. 요청은 계속 클라이언트 원장에 남고, 서버는 별도 내구성 큐에 접수하거나 쓰기를 대신 버퍼링하지 않는다.

## 기존 경로와 분리

`application(..., lookup_retry_after_seconds=None)` 기본값은 기존 응답 계약을 유지한다. 새 `ready_backpressure` 모드에서만 1을 설정한다. [v4 프로필](../examples/qualification/orders-lookup-backpressure-v4.json)에 이 차이를 고정하며, 기존 v3 `ready_bounded`와 같은 하네스로 각각 새 UUID 클러스터에서 실행한다. 기존 v1·v2·v3의 결과와 프로필을 덮어쓰지 않는다.

실제 HTTP response hook으로 받은 대기 안내를 요청 trace에 기록한다. 미지원 값은 원문 대신 `unsupported`로 표시하고, 응답이 없거나 전송되지 않은 시도에는 이전 응답의 안내를 붙이지 않는다. 이 관측은 실제 사용 중인 고정 이미지의 클라이언트 정책을 바꾸지 않는다.

두 경우 모두 접수 전 target Pod와 선택 라벨이 준비되지만 source만 현재 경로에 선택돼 있다. 목적지 INSERT의 실제 거부(SQLSTATE 42501), 워커·SA·이미지 바이트, 경로 PATCH 1회, 후속 수동 라벨 활성화 0회, 최초 부하 중 target 응답과 최종 SQL 대조를 검사한다. 정상 전환에는 작업자 고장을 주입하지 않는다.

## 검증과 해석

실제 TLS DB에서 앱의 정상 연결을 확인한 뒤 CONNECT 권한을 거두고, 권한 조회와 연결 실패·HTTP 503을 함께 확인한다. 연결 시작 단계의 libpq 거부는 SQLSTATE를 제공하지 않는 `OperationalError`일 수 있다. SQL 명령의 `InsufficientPrivilege`라고 추정하지 않는다. 권한 복구 뒤 실제 404·멱등 재제출·충돌 409·기존 데이터 보존도 확인한다.

추가 실제 loopback TCP 시험은 클라이언트가 GET의 1초 안내를 지키고, 60초 안내는 5초 기한을 늘리지 않고 중단함을 확인한다. 이는 통제한 HTTP 응답 시험이며 실제 장애나 전체 이전 완료 시험과 구분한다.

단일 closed-loop 실행마다 재시도로 요청 도착 시각이 달라진다. 한 번의 비교로 일반적인 개선율이나 무오류 SLO를 주장하지 않는다. 최초 503·연결 오류, 호출 내 소진, 부하 종료 후 복구와 별도 확인 주문은 계속 분리한다. 최종 SQL 일치가 모든 호출의 기한 충족을 뜻하지 않는다.

대상은 로컬 arm64 kind 한 노드와 전용 PG 서버의 별도 DB다. 계획·IdP·일부 증거·로컬 witness는 시험 fixture다. 실제 AWS→독립 온프렘 이전·운영 부하·WORM·기업 인증·금융 보안 인증은 별도이며, 제품 또는 기존 고객 앱에 이 정책을 자동 적용하지 않았다.

최초 비교는 별도의 [복원 스냅샷 경합](restore-snapshot-consistency.md)으로 완료되지 않았다. 해당 실패를 보존하고 제품 probe를 수정·별도 검증한 다음, 새 고정 이미지에서 두 모드를 함께 다시 측정한다. 예전 이미지의 실패와 새 이미지의 성공을 동일 조건의 backpressure 효과 비교로 합치지 않는다.

## 이번 결과

| 같은 수정 이미지의 경우 | 최초 실패 / 100건 | 호출 내 완료 | 최종 SQL 대조 |
|---|---:|---|---|
| 조회 안내 없음 | 3 (503 2·통신 1) | 완료 99·8회 한도 소진 1 | 후속 복구 뒤 103/103 |
| 조회 안내 1초 | 1 (503 1) | 완료 99·기한 소진 1 | 후속 복구 뒤 103/103 |

후보에서 조회 503 응답 4개 모두 실제 1초 안내를 확인했다. 그러나 남은 기한보다 다음 안내가 길어 호출 한도 충족에는 실패했다. 최대 호출 시간은 기준 2.710초·후보 4.411초이며, 후속 복구까지 포함한 최대 부하 주문 완료는 각각 26.393초·25.973초다. 응답 backpressure를 연결한 것이며 무중단·5초 내 전체 완료를 달성한 것은 아니다.

API·기한·멱등성 구성 요소 44건과 복원·이전 회귀 10건은 통과했다. 두 최종 클러스터 실행의 시계 감시·권한 거부·실제 소스·SQL 대조도 완료했고, 과거 실패 4종은 원문에 보존했다. 세부 수치와 서로 다른 시험 범위는 개발 기록에서 구분한다.
