# 이전 시스템의 프로덕션 자격 검토와 후속 개발 계획

2026-11-18 · 개인 Sova 개발 기록. 팀의 설계·담당·태스크·운영 정책을 변경하지 않는다.

## 1. 현재 판단과 근거 범위

현재 구현은 프로덕션을 고려한 안전한 이전의 기반이다. 모든 고객 앱의 무중단 이전을 운영 수준으로 검증한 제품이라는 판단은 보류한다. 구현을 부정하는 판단이 아니라, 지원 범위와 증거가 충분한지를 따지는 판단이다.

| 검토 기준 | 고정 기준 | 이번에 한 일 |
|---|---|---|
| 팀 platform | `develop`의 `61d44b1d042e5524c15e46330f60ccaf3733a64f` | 실행기·쓰기 차단·복구·태스크·앱 관련 이력의 읽기 전용 검토 |
| 개인 Sova | `feature/contract-driven-foundation`의 `03c4839a43551e303ebf3347021e926fce2d1274` | 구현 안내·운영 서비스·실측·probe·후속 계획 검토 |
| 개인 Security | `6a372685883be50f8f841a0c960a692d3bdcedec` | 통합 명세와 기존 패키지의 책임 경계를 참조 |

여기에 고정한 SHA는 검토한 소스 기준이다. 실제 배포 이미지 원본·현재 서버 상태·새로운 시험 통과를 뜻하지 않는다. 이번 작업은 문서화이며 새 실환경 실행, 성능 측정, 공유 자원 변경을 하지 않았다. 이후 미커밋 어댑터 작업도 이 검토의 통과 대상으로 합산하지 않는다.

### 이미 있는 강점

- 팀 실행기는 자원별 epoch·lease·멱등 키, 앱 역할 차단과 기존 세션 종료, barrier·내용 비교·시퀀스 보정, 불확실할 때의 SAFE_HOLD, 풀러 설정 영구 반영과 재확인을 구현했다.
- 개인 Sova에는 고정 계약·방향별 자격·서명 증거·효과 원장·정지 증명 기반 복구, 복수 writer probe, 실제 복제·이전·복귀 시험이 있다.
- T14·T19는 이전 전후 통제와 준비 상태 판정에, T36·T37은 품질 관측에, T21·T22는 승인·상태 표시와 사용자 재접속·전환 관찰에 기여한다. 데이터 실행기의 주담당과 이 기여를 구분한다.

### 아직 하나의 운영 자격으로 결합하지 못한 것

1. 사용자가 제출한 요청이 언제·어디서·몇 번 완료됐는지의 독립된 대조.
2. 실제 실행 설정·보안 정책을 유지한 전체 경로의 반복 부하·장애 시험.
3. 모든 등록 writer와 오래된 실행 주체의 재등장에 대한 차단.
4. 목적지 신규 쓰기 이후 실패와 복귀의 완전한 업무 결과 대조.
5. 코드·이미지·토폴로지·시나리오·원문 증거가 연결된 지원 자격과 만료·회수.

## 2. 논의에서 유지할 구분

| 표현 | 앞으로의 해석 |
|---|---|
| 쓰기 정지 | 실행기의 접수 정지부터 활성화까지. 사용자 전체 대기 시간과 별도 지표 |
| 서비스 연속성 | 제출·재시도·완료·결과 조회를 포함한 사용자 업무가 정해진 시간·오류 조건을 만족하는지 |
| 재접속 | 연결 복구 기능. 전환 중 데이터 유실·중복 없음이나 허용 시간 준수를 단독으로 증명하지 않음 |
| SAFE_HOLD | 불확실한 상황의 안전 조치. 쓰기 중단이 길어져도 가용성 PASS로 바꾸지 않음 |
| 계획된 이전의 유실 없음 | 시험에서 성공 응답한 요청 집합과 목적지의 영속 결과를 대조한 범위. 재해 장애 전체의 RPO=0과 다름 |
| 전체 이전 시간 | 조사·준비·복제·승인·전환·안정화의 합. 실제 서비스 중단 시간과 다름 |
| 실환경 시험 통과 | 고정된 방향·규모·설정·버전에서의 결과. 일반 고객 운영 지원과 별도 |

4,501ms 같은 단일 클라우드 기록뿐 아니라 후속 로컬·교차 클라우드 반복 측정도 존재한다. 모두 같은 자격의 표본은 아니다. 경로·버전·데이터량별로 나눠 보존하고, 소수 표본으로 p99나 운영 상한을 주장하지 않는다. 최신 수치와 조건은 [구현 안내](contract-foundation.md)의 정지 구간 측정 및 ADR-0004를 따른다.

## 3. 다음에 완성할 경로

**목표:** 기존 HTTP 주문 앱·PostgreSQL을 AWS에서 독립 Linux VM으로 이전하고, 사용자 업무와 복구 결과를 같은 실행에서 확인한다.

| 항목 | 첫 자격의 범위와 조건 |
|---|---|
| 업무 | 기존 `tests/postgres_business.py`의 주문·멱등 결과·작업 불변식을 재사용. 실제 HTTP 경유 업무 경로가 없으면 먼저 연결하며, DB 직접 쓰기를 HTTP 서비스 시험으로 표시하지 않음 |
| 데이터 | PostgreSQL 한 쓰기 권한 단위. 앱·배치 writer, 스키마·확장·시퀀스·트리거·2PC 설정·비교 대상의 목록 고정 |
| 전략 | 기존 offline-copy와 실제 논리 복제 snapshot-cdc를 별도 프로필로 비교. 이름이 같아도 전체 재복사 전략과 최종 변경분 적용 전략을 구분 |
| 접속 | 앱·DB·관리 경로에서 검증된 TLS. CA·호스트명 검증 실패를 평문·검증 해제로 우회하지 않음 |
| 운영 경로 | 저장 계획→독립 승인→운영 API→워커→실제 adapter→독립 probe→완료 보고. 시험 전용 직접 호출과 별도 |
| 실행 주체 | API·워커의 버전·UID·lease, 출발지·목적지의 writer/관리 도구·배치·복제 권한 등록 |
| 복구 | 목적지 신규 업무 이후 역방향 동기화·대조·재승인·원본 활성화. 준비 없는 자동 복귀 금지 |
| 외부 효과 | 첫 프로필에서는 외부 결제·메일·별도 큐 전달을 제외하고 제외 사실 명시. 발견되면 차단하거나 프로필을 확장해 재검증 |
| 사용자 세션 | 첫 HTTP 프로필은 장기 연결 유지 보장을 포함하지 않음. 채팅/WebSocket은 기존 앱으로 별도 연속성 프로필을 검증 |

이 경로를 선택했다고 기존 다른 어댑터를 삭제하지 않는다. 후보 지원과 운영 자격을 분리한다. 로컬 통과 뒤 AWS 자원·대상·비용·실행 시간을 확인하고 전용 환경에서만 실환경 인수를 진행한다.

## 4. 안전성·보안·연속성의 합격 기준

아래는 자격 시험의 설계 요구사항이다. 고객의 숫자 SLO나 실제 시험 결과가 아니다.

| 영역 | 필요한 관측과 판정 | 현재 새 인수 상태 |
|---|---|---|
| 성공 응답한 업무 | 클라이언트가 성공 응답을 받은 요청 ID의 영속 결과가 목적지에 모두 존재. 주문과 결과 기록의 의미도 일치 | 미실행 |
| 중복·재시도 | 같은 업무 멱등 키의 네트워크 재전송은 한 결과로 수렴. 다른 tenant/업무의 키와 충돌하지 않음 | 미실행 |
| 응답 유실 | 커밋 뒤 응답을 잃은 요청을 같은 ID로 조회·재시도해 결과 확정. 불명 상태는 성공으로 추정하지 않음 | 미실행 |
| 단일 writer | 모든 등록 writer·기존 세션·오래된 경로를 확인. 미등록 쓰기 경로 발견 시 목록 수정과 재평가 전까지 차단 | 미실행 |
| 연속성 | 최초 시도 오류율, 재시도 후 최종 오류율, 사용자 전체 완료 시간, 최장 무응답, 정지·재접속 시간을 각각 기록 | 미실행 |
| 복귀 | 목적지에서 새로 확정된 주문까지 원본에 보존. 복귀 중에도 단일 writer·결과 조회 충족 | 미실행 |
| 보호 수준 | 필요한 최소 기준과 이전 전후 통제를 함께 검사. 원본이 취약하다는 이유로 같은 취약점을 허용하지 않음 | 미실행 |
| 운영 설정 | NetworkPolicy·인증·TLS·제한 권한을 켠 같은 배포에서 통과. 완화해서 얻은 수치는 자격에서 제외 | 미실행 |
| 관측 신뢰 | 클라이언트·서비스·DB·효과 원장 자료를 연결. 수집 누락·관측기 장애는 UNKNOWN 또는 시험 무효로 남김 | 미실행 |

### 지표와 요청 원장

- 각 논리 요청에는 `run_id`, tenant, 업무 ID, 멱등 키를 부여한다. 전송 시도별 `attempt_id`는 따로 둔다.
- 독립 부하 생성기가 제출 의도·시도·응답·최종 조회를 내구성 있게 기록한다. 서버 결과와 대조하며 한쪽 기록만으로 성공을 만들지 않는다.
- 집합을 제출, 성공 응답, 명시적 거부, 결과 불명으로 구분한다. 시험 종료 후 결과 불명을 별도 조회해 분류하고, 끝내 해결되지 않으면 미해결로 남긴다.
- 최초 오류와 최종 성공을 함께 표시한다. 예상된 부정 보안 probe의 거부는 사용자 업무 오류율에 섞지 않는다.
- 총 지연은 첫 제출부터 결과 확인까지 클라이언트의 단조 시계로 잰다. 재시도로 타이머를 초기화하지 않는다. 서로 다른 호스트의 단조 시각을 직접 빼지 않는다.
- 계획된 제출률과 실제 제출률, 동시 요청·재시도량, 타임아웃·완료되지 않은 요청도 보존한다. 서버가 느려져 생성기가 요청을 덜 보내는 현상을 좋은 지연으로 해석하지 않는다.
- 표본 수와 관측 구간을 함께 공개한다. 장시간 정지·중단된 실행을 성공 실행 평균에서 빼지 않는다.
- 허용 쓰기 지연·최종 오류율·복구 시간, 데이터량·제출률·반복 횟수는 프로필 등록 때 정한다. 미정이면 성능 자격은 발급하지 않는다. 5초 같은 임의 숫자를 운영 SLA로 확정하지 않는다.

## 5. 장애 시험표

| 주입 위치·사건 | 확인할 조건 |
|---|---|
| 접수 정지 전·직후 워커 종료 | 중복 효과 없이 다음 주체가 증명·관측으로 재개. 정지 해제는 목적지 비활성 확인 후 |
| 원본 차단 도중 앱·배치 재시작 | 재시작한 writer의 새 연결도 거부. 관리자가 되살린 권한은 보류·경보로 연결 |
| prepared transaction·긴 트랜잭션 | 지원 설정과 실제 잔존 상태 확인. 예산 초과나 미확인 시 다음 활성화 차단 |
| barrier 지연·복제 slot/WAL 보존 상한 | 뒤처짐·보존 손실·구독 재생성으로 근거가 바뀌면 재평가. 이전 barrier를 재사용하지 않음 |
| 목적지 활성화 성공 직후 응답 유실 | 원래 실행이 실패했다고 추정해 출발지를 열지 않음. readback으로 실제 권한 확인 |
| lease 만료 후 옛 워커 재개·API 단절 | 새 워커와 효과 경합 금지. lease 만료만으로 옛 원격 효과가 불가능해졌다고 가정하지 않음 |
| 경로 전환 중 풀러·앱·Edge 재시작 | 메모리 상태만이 아닌 영구 설정·현재 경로·새 세션 응답 확인. 오래된 경로 쓰기 거부 |
| 목적지 신규 쓰기 후 실패 | 신규 업무를 보존하는 역방향 계획 검증. 동기화 불가·양쪽 상태 불명 시 쓰기를 추가 개방하지 않음 |
| 제어 DB 복원·witness 접근 불가 | 예전 epoch·승인으로 실행 재개 금지. 외부 witness와 복구 규칙으로 상태 판단 |
| 출발지 snapshot 복원·복제본 승격 | 새 자원 UID와 쓰기 권한을 재조사. 원본 차단이 실제로 유지되는지 확인 |
| 인증서·token·권한 만료·철회 | 정상 연결과 잘못된 CA·호스트·다른 tenant·권한 회수의 부정 대조. 실패를 우회하지 않음 |
| 관측·감사 수집 중단 | 누락된 창을 PASS로 채우지 않음. 보류 이유와 누락 구간 보존 |

네트워크 분할 때는 어떤 원격 효과가 계속될 수 있는지 따로 정한다. 데이터 안전성을 위해 길게 멈출 수 있는 실패와 자동 복구할 수 있는 실패를 지원 프로필에 적는다. 모든 장애에서 무중단을 약속하지 않는다.

| MQ-03 | 같은 배포에서 이전·신규 쓰기·복귀 연결 | 실 운영 API/워커 경유. 직접 DB 시험과 분리된 결과·원문 증거 | 계획 |
| MQ-04 | 장애표의 결정 경계별 주입 | 재개·보류·복귀 분류와 업무 결과 대조. 기존 fault/recovery 시험을 재사용하고 빈 접점만 구현 | 계획 |
| MQ-05 | 부하·네트워크·데이터량별 반복 | 모든 시도와 실패 포함, 안전·연속성·보안·복구 별도 판정. 표본 수와 한계 공개 | 계획 |
| MQ-06 | 지원 자격과 운영 인수 | 정확한 릴리스·방향·토폴로지·보장·유효 기간에 결속. runbook·회수·알림·복구 담당 확인 | 계획 |

**다음 실제 개발 단위는 MQ-01과 MQ-02의 최소 연결이다.** 아직 HTTP 경로·원장 대조가 확인되지 않았으므로 기존 DB 시험 성공으로 닫지 않는다. MQ-01/02를 통과하기 전 성능 최적화나 새 저장소 확대를 다음 통합 목표로 삼지 않는다.

독립 라이브러리를 새로 만들지 않고 기존 `tests/postgres_business.py`, `tests/handoff_drive.py`, `tests/perf/test_handoff_pause.py`, `tests/perf/test_cloud_handoff_pause.py`, 서비스 API/워커, Security 증거·보류와 OTel 연결을 먼저 조사한다. 기존 DB fixture는 HTTP 서비스나 외부 생성기를 이미 제공한다는 뜻이 아니다.

## 7. 정지 구간을 줄일 때의 선택 기준

- 먼저 현재 실측으로 복사·검증·권한 변경·원격 연결·경로 확정 시간을 나눈다. 가장 긴 부분을 확인하기 전에 풀러나 복제 도구를 바꾸지 않는다.
- 최종 비교와 복원 검증의 범위는 [ADR-0004](adr/0004-verification-inside-the-window.md)를 따른다. 사전 검증을 재사용하려면 최종 데이터·설정 변경을 놓치지 않는 유효성 조건과 재평가가 있어야 한다.
- DB 안 지문, 연결 재사용, 증분 검증을 검토하되 자료형 정규화·schema 변화·실제 TLS·원장 기록을 보존한다.
- PgBouncer 대기나 앱 재시도를 넣어도 클라이언트 deadline·취소·멱등성·대기 상한·재시작 후 요청 상태를 검증한다. 오류를 숨기거나 끝없이 기다리는 방식은 선택하지 않는다.
- 숫자 SLO를 현재 전략으로 만족하지 못하면 NEEDS_EVIDENCE/미충족으로 남긴다. 계약을 몰래 완화하지 않는다.

## 8. 보고서와 운영 자격의 증거

실행 보고서는 다음을 한 묶음으로 연결한다.

1. 계약·계획·승인 digest, source SHA, 이미지 digest, schema·설정·보안 정책 revision.
2. 방향·자원 UID·writer 목록·실행 권한·인증서/신뢰 식별자. 비밀값은 포함하지 않음.
3. 부하·데이터량·네트워크 조건·시간 동기화 오차와 독립 요청 원장.
4. 단계·효과·오류·보류·관측 원문, 검증기 버전·서명·보존 위치·완전성 정보.
5. 각 보장의 PASS/BLOCK/UNKNOWN, 제외한 기능·장애, 실패·중단 실행, 자격 만료·회수 조건.

서명은 내용과 발행자를 연결할 뿐 관측의 완전성과 진실성을 단독으로 증명하지 않는다. 보존 저장소의 접근·삭제·복원 시험도 별도로 필요하다. 긴급 정지·복구는 현재 승인·보안 보류·재승인 경계를 재사용한다.

## 9. 남기는 질문과 재검토 방법

| 질문 | 다음에 확인할 근거 |
|---|---|
| 현재 짧은 쓰기 정지가 사용자 요구를 충족하는가? | MQ-02/05 사용자 지연·오류·부하 결과 |
| 중앙 lease가 있어도 옛 원격 실행을 확실히 멈출 수 있는가? | MQ-04 정지 증명·네트워크 단절·지연 효과 시험 |
| writer 목록이 충분한가? | 실제 권한 그래프·배치/재시작 목록, 누락 writer를 의도적으로 넣은 거부 시험 |
| 복귀를 자동화해도 되는가? | 신규 업무·외부 효과·역방향 복제·복원본을 포함한 복구 결과 |
| Kubernetes가 반드시 필요한가? | 같은 계약의 VM 실행 경로와 비교. 배포 backend와 이전 프로토콜을 분리 |
| 현 운영 인수 없이 금융 수준이라고 표현해도 되는가? | 안 됨. 규제 대응표·운영 통제·독립 검토·복구 인수 결과를 별도 제시 |

새 판단은 날짜·기준 SHA·검증 환경·관측·선택 이유·남은 한계를 기록한다. 기존 실패를 삭제하지 않고 해결 커밋과 재시험으로 연결한다. 사용자 요청의 안전·연속성을 충족하는 근거가 늘었을 때 다음 범위를 확장한다.
