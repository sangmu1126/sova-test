# 시험 DB 준비와 클러스터 기동 순서

2026-11-19 · 개인 브랜치 `feature/migration-request-qualification`.

## 변경 이유

직전 후속 기동 실행은 업무 부하가 시작되기 전에 `ServiceJourney`가 source DB의 버전을 읽다가 2초 연결 시간 초과로 중단됐다. 이것을 이전 실행 실패율 0건이나 복구 성공으로 집계하지 않았다.

버전은 전용 PostgreSQL 서버의 기초 정보이며 클러스터 기동 뒤에 다시 연결해 읽을 필요가 없다. 이번에는 **실제 source·target DB 버전 관측을 kind 기동 전에 마치고**, 그 기록을 서비스 fixture 준비 단계에 전달한다. 이 변경으로 과거 시간 초과의 근본 원인이 CPU·메모리 경합이었다고 단정하지 않는다.

| 단계 | 수행 내용 |
|---|---|
| 전용 DB 준비 | 실행별 TLS DB·서버·CA·클라이언트 인증과 격리 확인 |
| DB 버전 관측 | 실제 두 DB에 연결해 이름·버전·TLS 상태를 조회. 재시도 없음 |
| 클러스터 기동 | UUID kind 생성·고정 이미지 반입·API/노드 신원 확인 |
| 서비스 준비 | 같은 DB 쌍의 관측값을 사용. 승인·증거는 기존 시점에 생성 |
| 실제 실행 | 기존 권한·fencing·Pod 중단·복구·HTTPS·독립 SQL 대조 그대로 |

## 기록의 의미

`ObservedDatabaseVersions`는 시험용 읽기 결과다. DB 이름 쌍이 현재 fixture와 다르면 거부한다. 실제 관측 시각·TLS 상태는 `database-bootstrap.json`에 남긴다. DSN·키·토큰·연결 비밀번호는 기록하지 않는다.

이 기록은 서명된 증거나 운영 승인·신원 인증을 대신하지 않는다. 실제 실행 중 연결·권한·TLS 검사를 건너뛰지 않으며 `qualification_issued`와 `authorizes_execution`은 모두 false다. 제품 이미지와 source·target DB의 운영 연결 설정은 변경하지 않았다.

## 그대로 유지하는 조건

- DB 연결 제한 2초, 클라이언트의 네트워크·완료·시도 한도 유지.
- 최초 버전 관측 실패는 자동 재시도 없이 전파.
- 실제 장애를 저장된 버전 정보로 성공 처리하지 않음.
- 사람이 승인한 범위·도메인 상태 전이·lease·복구 조건 유지.
- 공유 kind·사용자 kubeconfig·클라우드 자원 변경 없음.

## 실제 실행 결과

고정 하네스 `ad21e7747fe2d48f8f9694f994ae8e8f1c7b276b`에서 세 로컬 통합시험 모두 완료했다. 제품 이미지는 기존 `sha256:bf94bd18080210a11900913116adf4de144e84a538fbbc25d9b101640574633a`를 그대로 사용했다.

|---|---:|---|---|---:|

| 목적지 사전 준비·부하 후 복구 | 18 (503 14·통신 4) | 한도 재시도 미사용 | 103/103 | 22.568초 |

세 실행에서 DB 버전 관측은 실제 클러스터 생성보다 먼저 끝났다. 이후 실제 worker·SA·image 신원, Secret/권한 없는 Pod 조회의 403, lease만 만료된 live owner의 복구 거부, 정상 Pod 삭제 뒤 후속 워커의 조회 전용 복구, 경로 PATCH 1회, 잘못된 CA/호스트명 거부를 확인했다. 기존 주문 50건도 유지됐다.

**이는 세 경로의 데이터·복구 시험 통과다.** 최초 실패 20·18·1건은 지우지 않는다. 한도 재시도 1건은 8회 한도를 소진했으며 이후 복구로 완료됐다. 최종 완료를 5초 이내 성공으로 소급하지 않는다. 단일 closed-loop 실행마다 도착 시각이 다르므로 일반적인 개선율이나 무중단 SLO로 해석하지 않는다.

## 검증 범위

전용 TLS DB에서 실제 버전 전달, 이후 연결 실패의 비우회, 최초 시간 초과의 비재시도, 다른 DB 기록 거부를 시험했다. 추가로 기존 서비스의 실제 HTTP·DB 흐름을 함께 실행했다. 고장 주입 시험과 실제 클러스터 실행 결과는 구분한다.

원문·고정 소스·실제 Pod 실행 결과는 아래 기록에 연결한다. 이 준비 순서 변경만으로 무중단이나 운영 부하 SLO를 발급하지 않는다.

[개발 기록](development/database-bootstrap-order-2026-11-19.md) · [검증 증거](evidence/database-bootstrap-order-20261119.json).

대상은 로컬 kind 한 노드와 같은 전용 PostgreSQL 서버의 별도 DB다. AWS→독립 온프렘 운영 이전, 기업 인증·WORM 저장소·실제 고객 부하 자격은 별도다.

후속으로 [준비된 목적지의 정상 전환](ready-target-cutover.md)을 별도 v3 프로필로 분리했다. 위 세 경우의 장애 주입·오류·복구 결과는 그대로 보존하며 정상 전환 결과로 바꾸지 않는다.
