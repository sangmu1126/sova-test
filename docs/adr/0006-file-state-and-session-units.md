# ADR-0006 · 파일 상태·세션 단위와 애플리케이션 한 단위 인계

- 날짜: 2026-11-17
- 상태: **채택**, 구현됨. 로컬 kind에서 실측했다.
- 관련: [ADR-0001](0001-contract-driven-foundation.md), [ADR-0005](0005-operational-service.md), [구현 안내 · 파일 상태·세션·애플리케이션 단위](../contract-foundation.md#파일-상태세션애플리케이션-단위-2026-11-17).

## 맥락

지금까지의 데이터 adapter는 DB, 객체 저장소, 메시지 브로커였다. 이 저장소들에는 권한 목록이 있어서, 권한을 회수하면 쓰기가 막힌다. 그런데 흔한 웹 앱(데모 게시판·게임 서버 포함)은 상태를 이렇게도 둔다.

- 볼륨 위의 파일: SQLite DB, 업로드 폴더
- 프로세스 메모리: WebSocket으로 이어진 경기·채팅 세션

둘 다 회수할 권한 목록이 없다. 볼륨은 마운트한 프로세스면 누구나 쓴다. 메모리 세션은 프로세스가 죽으면 사라진다. 또한 앱은 이런 상태를 여러 곳에 함께 둔다. 그래서 한 앱을 한 번의 쓰기 정지로 옮기려면, 여러 adapter를 한 단위로 묶어야 한다.

조건은 기존 안전 규칙을 바꾸지 않는 것이다.

- 단일 권한(`PLANNED_SINGLE_AUTHORITY`)
- readback은 읽는 대상을 바꾸지 않음
- 측정은 adapter와 따로 함
- 증거는 서명된 것만 받음

## 결정 1 · 볼륨의 writer는 그것을 마운트한 워크로드다

파일 시스템에는 회수할 권한이 없다. 그래서 쓰기에 관한 사후조건은 모두 Pod에 관한 진술로 바꾼다.

- **승인 중지.** 앱 writer(Deployment·StatefulSet은 0으로, CronJob은 정지)를 멈추고, 그 Pod가 남지 않을 때까지 기다린다(상한 있음). 파일 상태 앱에는 읽기 전용 모드가 없으므로, 이 시간이 곧 다운타임이다. 계약의 쓰기 정지 예산이 이를 정한다.
- **차단.** 등록된 writer를 모두 멈춘다. 확인 조건은 원본 claim을 읽기·쓰기로 마운트한 Pod가 하나도 없는 것이다. 등록 여부, 종료 중인지와 상관없다. 사람이 띄운 Pod가 claim을 쥐고 있으면 차단은 미확인으로 남는다.
- **활성화.** 목적지 앱 writer를 등록된 replica로 올리고, 앱의 Pod 말고는 목적지 claim을 쓰지 않는 것을 확인한다.

## 결정 2 · 파일은 API 서버를 거친 agent Pod로 옮긴다

복사는 짧게 사는 agent Pod 둘이 한다. 원본에는 읽기 전용으로, 목적지에는 읽기·쓰기로 마운트한다. 워커는 API 서버의 Pod 프록시로 agent와 통신한다.

- 두 클러스터 사이 복사에도 등록된 API 서버 두 곳 말고는 필요한 것이 없다. 노드 사이 직접 연결이나 LoadBalancer를 열지 않는다.
- agent는 표준 라이브러리만 쓰는 파일 하나다. 고정된 Python 이미지에서 `python3 -I -c`로 실행하므로, 이미지를 따로 만들지 않는다. Pod annotation에 소스의 SHA-256을 남긴다.
- 경로는 claim 루트부터 구성 요소마다 `O_NOFOLLOW`로 연다. 볼륨 안의 심볼릭 링크는 링크로 기록하고 따라가지 않는다.
- 쓰기는 임시 이름에만 허용한다. 최종 이름은 원본 SHA-256과 일치를 확인한 뒤의 rename으로만 얻는다.
- 토큰은 워커 키와 Pod 이름에서 HMAC으로 만든다. Pod spec에는 그 digest만 들어간다. 그래서 어느 워커 인스턴스든 다른 인스턴스가 띄운 agent와 통신할 수 있다.
- agent는 root로 돌지 않는다. 소유자를 바꿀 수 없으므로, 다른 사용자의 파일은 "복사됨"이 아니라 "다름"으로 읽힌다.
- readback은 이미 bound된 claim에만 읽기 전용 agent를 띄운다. claim을 bind하는 것은 준비 단계다. 그래서 readback은 읽는 대상을 바꾸지 않는다.
- 갱신(2026-11-19): 워커의 한 실행 안에서는 읽기 agent를 지우지 않고 다음 단계·probe에서 다시 쓴다. adapter와 probe는 각자의 agent를 따로 남긴다. 쓰기 agent와 ReadWriteOncePod claim의 agent는 매번 지운다. 실행이 끝날 때와 활성화 직전(목적지 claim의 agent 모두)에 지운다. 정리하지 못한 agent는 10분 동안 요청이 없으면 스스로 끝난다. 남긴 agent는 Pod 자리를 차지한다. 그래서 새 agent가 자리가 없어 스케줄되지 못하거나 Pod quota로 거부되면, 같은 클러스터에 남긴 쉬는 agent를 모두 지운다. 활성화 직전에도 앱 Pod를 위해 그렇게 한다(#41).

내용은 모든 항목의 manifest로 비교한다(경로, 종류, mode, 소유자, 크기, SHA-256 또는 링크 대상). manifest가 같으면 바이트 단위로 같은 트리다.

갱신(2026-11-19): manifest에 하드 링크 묶음(같은 파일을 가리키는 경로들)도 싣는다. 같은 파일을 나누는 경로까지 같아야 같은 트리다. 복사는 묶음마다 내용을 한 번 쓰고 나머지 경로는 링크한다.

**대안과 기각 이유.**

- 노드 사이 rsync: 클러스터 사이에 데이터 경로를 새로 열어야 한다.
- CSI snapshot: 저장소 구현마다 다르고, 로컬 볼륨에는 없다.
- exec 스트리밍: 워커에 exec 권한이 필요하고, WebSocket·SPDY 처리가 필요하다.

## 결정 3 · probe는 다른 방법으로 잰다

볼륨 probe는 adapter의 readback과 다른 방법으로 잰다.

- **쓰기 거부.** 각 writer Pod에 앱 자신의 쓰기 probe를 실제로 보낸다. probe는 쓴 것을 되돌린다. 연결되지 않는 Pod는 쓸 수 있는 것으로 센다. 등록되지 않은 읽기·쓰기 마운트도 실패로 본다. 짧은 관측 동안 트리가 바뀌지 않아야 한다(등록되지 않은 쓰기도 드러나게).
- **SQLite 내용.** agent의 scratch(emptyDir)로 DB와 WAL을 복사한 뒤 논리적으로 비교한다. 무결성 검사, 스키마, 테이블별 행 집합을 본다. 볼륨의 파일을 SQLite로 직접 열지 않는다(여는 순간 `-shm`이 쓰이고 로그가 checkpoint된다).
- **업무 불변식.** 등록된 읽기 전용 질의로 확인한다(위반 행 0개, 또는 참조한 파일이 모두 있음).
- **복원 훈련.** 목적지를 새 scratch claim으로 복원해 비교한 뒤 지운다.
- **교차 테넌트.** 목적지 namespace의 어떤 claim도 다른 테넌트 claim의 볼륨에 bound되어 있지 않아야 한다. 해제된 볼륨을 넘겨받는 경로를 보는 것이다.
- **전송 암호화.** API 서버에서 agent Pod까지는 클러스터 네트워크의 평문 HTTP다. 그래서 검증된 전송 암호화를 요구하는 계약에서는 실패로 측정한다. 충족했다고 가정하지 않는다.

## 결정 4 · 메모리 세션은 옮기지 않고 drain한다, 단일 권한 안에서

명세(§18.2)는 WebSocket·장기 연결을 "drain·종료·재연결을 계약으로" 처리하라고 한다. 그러나 원본과 목적지가 세션을 동시에 받는 프로필은 정의하지 않는다(이전 프로필은 모두 데이터 권한 기준이다). 그래서 단일 권한 안에서 처리한다.

- **승인 중지.** 원본 Pod를 경로에서 뺀다. Service selector를 Pod가 없는 "paused" 쪽으로 옮기므로, 새 연결은 즉시 거부된다. 그다음 이미 열린 세션이 끝나기를 기다린다. 템플릿의 이 단계가 보장하는 "진행 중 작업 분류"가 바로 이것이다. 이미 맺어진 연결은 커널 연결 추적(iptables 모드 kube-proxy) 덕분에 계속 흐른다.
- **세션 수는 앱이 아니라 커널이 센다.** 원본 Pod마다 ephemeral container를 붙인다. 이 컨테이너는 Pod의 네트워크 namespace만 공유하고, 1초마다 서비스 포트의 ESTABLISHED 연결을 `/proc/net/tcp`에서 읽어 쓴다. 노드 IP(kubelet probe)에서 온 연결은 제외한다. 15초보다 오래된 값이나 관찰자 없는 Pod는 "모름"이다.
- **drain 상한.** `drain_seconds`를 멈춘 시각(원본 워크로드 annotation)부터 센다. 넘기면 정책에 따른다.
  - `hold`: 세션이 끝나거나 운영자가 정할 때까지 미확인으로 둔다.
  - `terminate`: 다음 단계로 가고, 차단이 끊을 세션 수를 증거로 남긴다. 그 클라이언트는 새 경로로 목적지에 다시 연결한다.
- **내구 상태는 없다.** 복사·확인 단계는 할 일이 없으며, 증거에 그렇다고 적는다.

**새 연결 측면의 비용.** 이 방식은 새 세션 쪽에서 drain 시간만큼의 정지를 낳는다. 원본·목적지가 동시에 세션을 받는 방식(전환 뒤 drain)은 무중단이지만, 명세에 없는 프로필이 필요하다. 이 ADR은 그 프로필을 만들지 않는다.

## 결정 5 · 애플리케이션은 구성 요소의 합으로 한 단위가 된다

`CompositeHandoffAdapter`는 각 행동을 모든 구성 요소에, 등록된 순서대로 수행한다. readback은 모든 구성 요소가 APPLIED일 때만 APPLIED다. 각 구성 요소는 같은 명령을 자기 adapter ID로 받는다.

측정은 의무의 성격에 따라 나눈다.

- **쓰기·권한·위치에 관한 의무.** 모든 구성 요소에 묻고, 모두 성립할 때만 통과한다.
- **내용·불변식·복원·목적지 데이터 통제.** 데이터를 가진 구성 요소가 답한다.
- **시간 예산.** 계획의 단계 시각으로 한 번 잰다.

데모 구조에서는 게임 세션을 먼저 drain한다. 그동안 게시판은 계속 쓰기를 받고, 그다음 멈춘다.

## 결정 6 · readback 증거는 8KiB 안으로 줄인다, 거부하지 않는다

`EffectObservation`은 증거를 8KiB까지만 받는다. 그런데 모든 adapter가 64KiB 한도로 증거를 만들고 있었다. 그래서 많이 본 readback(다른 파일이 많을 때, 테이블·파티션이 많을 때)은 판정 대신 `ContractError`로 끝났다.

이제는 증거를 줄인다.

- 긴 목록부터 줄이고, 무엇을 줄였는지 적는다.
- 전체 증거의 digest를 남긴다.

적합성 시험은 실제 한도를 확인한다.

## 결과

- 볼륨: 적합성 9 + 고유 3, probe 실패 시험 3을 통과했다. 결함 주입 2건(등록되지 않은 Pod 무시, 원본에서 지운 파일 미삭제)을 잡았다.
- 세션: 3개를 통과했다. 결함 주입(drain 무시)을 잡았다.
- control plane 전체 흐름 두 가지가 모든 의무 pass로 HANDOFF_COMPLETE에 도달했다.
  - 볼륨 단독: 쓰기 정지 27.5초
  - 게시판 + 게임 서버 한 단위: 쓰기 정지 32.5초(진행 중 경기 drain 15초 포함). 그 경기는 원본에서 정상 종료됐다.

## 한계

- 볼륨 내용 비교는 매번 양쪽의 모든 바이트를 읽는다. 큰 볼륨에서는 확인 시간이 크기에 비례한다. 쓰기 정지 안의 확인 비용을 줄이는 일은 ADR-0004와 같은 과제다.
- agent는 소유자를 바꾸지 못한다. root로 돌지 않기 때문이다. 원본 파일이 여러 사용자 소유라면 비교가 실패한다(의도한 동작).
- 블록 모드 볼륨, 특수 파일(소켓·FIFO, 거부), 심볼릭 링크에 건 하드 링크(거부)는 다루지 않는다. ~~하드 링크(별개 파일로 복사)~~ → 볼륨 안의 하드 링크는 보존한다(2026-11-19).
- ReadWriteOncePod 볼륨은 앱이 도는 동안 agent가 마운트할 수 없다. 그래서 start_sync를 쓸 수 없다. offline copy는 차단 뒤라 가능하다.
- API 서버에서 agent Pod까지는 평문이다. 검증된 전송 암호화를 요구하는 계약은 이 단위에서 실패로 측정된다.
- 세션 drain은 kube-proxy가 이미 맺어진 연결을 유지하는 것(iptables·IPVS의 일반 동작)에 기댄다. 다른 데이터 경로(일부 Ingress, 서비스 메시)에서는 따로 확인해야 한다.
- 관리형 클러스터와 클러스터 사이 볼륨 복사는 실측하지 않았다. 시험은 한 kind 클러스터 안의 두 claim으로 했다.
