# ADR-0004 · 정지 구간 안의 검증 비용: 서버 쪽 digest, 복원 훈련은 현행 유지

- 날짜: 2026-11-15
- 상태: **채택**(서버 쪽 digest), 복원 훈련은 **현행 유지**. 2026-11-15.
- 관련: [ADR-0003](0003-target-controls-before-the-pause.md), [구현 안내 · 클라우드 사이 직접 인계](../contract-foundation.md).

## 맥락

ADR-0003 뒤에도 offline-copy의 클라우드 간 인계(1만 행)에는 최종 검증부터 활성화까지 약 7초가 남았다. 이 구간에서 쓰기는 멈춰 있다. 단계별로 나누면 원인은 둘이다.

1. **같은 내용 비교의 반복.** 정지 구간 안에서 다음 비교가 모두 양쪽 DB의 모든 행을 플랫폼 프로세스로 읽어 와 digest를 냈다.
   - 복사 확인(adapter readback)
   - 최종 검증(adapter readback)
   - 보호 데이터 비교 의무(표마다 probe)

   목적지가 다른 클라우드에 있으면 이 읽기가 인터넷 경로를 여러 번 오간다.
2. **복원 훈련.** `tested_restore`는 목적지 표를 이 프로세스를 거쳐 빈 DB에 다시 쓰고 비교한다. offline-copy에서는 정지 전 목적지가 비어 있어 이 시험을 앞으로 옮길 수 없다(ADR-0003).

복원 훈련을 두 가지 방법으로 쟀다(`tests/perf/test_restore_drill_options.py`, 1만 행, 3회씩).

| 목적지 | 클라이언트 복사(현행) | 서버 안 복제(`CREATE DATABASE … TEMPLATE` + 서버 digest) |
|---|---|---|
| Cloud SQL | 2271 / 2488 / 2600 ms | 1899 / 1079 / 1054 ms |
| RDS | 2878 / 2881 / 3550 ms | 2099 / 1321 / 1322 ms |

## 결정 1 · 내용 digest는 데이터가 있는 서버에서 계산한다(채택, 구현됨)

- `postgres_digest.table_digest`는 지금까지의 digest와 **같은 값**을 SQL로 계산한다.
  - 정의: 행 수, 그리고 각 행 텍스트(UTF-8)를 바이트 순으로 정렬하고 8바이트 big-endian 길이를 앞에 붙여 이은 것의 SHA-256.
  - 표 크기와 상관없이 해시 하나만 네트워크를 건넌다.
  - 이전 증거와 이후 증거를 그대로 비교할 수 있다. 모든 값 종류(유니코드, NULL, 중복 행, 배열, JSON, bytea, 무한대·NaN·음의 0)에서 서버 값과 클라이언트 값이 같음을 시험으로 고정했다.
- **세션 설정 고정.** 행의 텍스트 형태는 시간대·날짜/간격 형식·부동소수 자릿수·bytea 출력 형식에 따라 달라진다. 지금까지는 이를 고정하지 않았다. 그래서 기본값이 다른 두 서버(예: 시간대가 다른 관리형 DB)에서는 같은 데이터도 다르다고 판정될 수 있었다. 두 방식 모두 트랜잭션 안에서 이 설정을 고정한다. 세션 설정을 바꿔도 digest가 변하지 않음을 시험으로 고정했다.
- **메모리 한도.** 서버는 한 표의 정렬된 행을 메모리에 모아 해시한다. 표가 256MiB를 넘으면 클라이언트 스트리밍으로 같은 digest를 낸다.
- adapter의 확인과 probe의 비교가 모두 이 함수를 쓴다.

## 결정 2 · 복원 훈련은 현행 유지

| 선택지 | 판단 |
|---|---|
| A. 클라이언트 복사(현행) | **유지.** 비교는 이제 서버 digest라 그만큼 줄었다. 복사는 남는다 |
| B1. 서버 안 복제(TEMPLATE) | 채택하지 않음. 1만 행에서 1~2초 빠르다. 하지만 ① 훈련 때마다 DB를 만들고 지워야 해 플랫폼에 `CREATEDB` 권한이 더 필요하다. ② 복제 순간 원본 DB에 다른 연결이 하나도 없어야 해 활성화 뒤(`operations.restore_test`)에는 쓸 수 없다. ③ "복원"이 아니라 "복제"를 시험한다 |
| B2. 사업자 백업·복원 | 정지 구간 안에는 둘 수 없다(수 분). 활성화 뒤 운영 복원 시험의 실제 구현 후보로 남긴다 |
| C. 정지 전 리허설 | 명세의 "리허설 통과"(§15.3 `TARGET_PREPARED`). snapshot-cdc 템플릿이 이미 하는 방식이다. 초기 동기화 뒤 컷오버 확인에서 복원 훈련을 하고, ADR-0003으로 정지 구간 밖에 둔다. 정지 예산이 빠듯한 서비스는 계획 탐색에서 snapshot-cdc를 고르게 하는 것이 맞다 |

offline-copy의 정의는 "모든 복사가 차단 구간 안에서 일어난다"이다. 그래서 최종 데이터에 대한 복원 훈련도 그 안에 남는다. 이 비용을 받아들일 수 없으면 템플릿을 바꾸는 것이 올바른 처방이다.

## 측정

같은 조건(1만 행, 경로마다 5회)에서 세 판의 쓰기 정지(최소 / 중앙값 / 최대, ms). 측정 시각이 달라 네트워크 차이도 섞여 있다.

| 경로 | v1 | v2 (ADR-0003) | v3 (+서버 digest) |
|---|---|---|---|
| RDS → Cloud SQL | 13556 / 20226 / 21222 | 11295 / 11525 / 12378 | 10525 / 10901 / 13253 |
| Cloud SQL → RDS | 12386 / 13998 / 17607 | 11433 / 12442 / 13382 | 10674 / 10927 / 11305 |
| Cloud SQL → 로컬, 논리 복제 | 7959 / 11477 / 14581 | 5889 / 6002 / 6103 | 5750 / 6210 / 8325 |
| RDS → 로컬 | 6114 / 6365 / 12072 | – | 5848 / 6140 / 6373 |
| Cloud SQL → 로컬 | 4991 / 5187 / 5742 | – | 5096 / 5265 / 8108 |

서버 digest의 효과는 기대보다 작았다. 클라우드 간 경로의 중앙값이 0.6~1.5초 줄었고, 목적지가 로컬인 경로는 차이가 없다(로컬에서는 행을 읽어 오는 비용이 원래 작다). 클라우드 간 경로의 최종 검증부터 활성화까지 남은 약 6초는 두 가지다. 하나는 남긴 복원 훈련(약 3초)이다. 다른 하나는 단계마다 원격 DB에 새로 맺는 연결(TLS·인증 왕복)로 보인다. 정지 구간 안에서 연결 수십 개를 새로 맺는다. 같은 단계 안의 연결 재사용이 다음 개선 후보다. 이번에는 측정 근거를 만들지 못해 결정하지 않았다.
