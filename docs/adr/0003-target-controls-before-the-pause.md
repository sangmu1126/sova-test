# ADR-0003 · 목적지 통제 시험은 쓰기 정지 전에, 활성화 의도에서는 유효성만 재확인

- 날짜: 2026-11-15
- 상태: **채택**, 2026-11-15. 계획 컴파일러 `sova-plan-compiler.v2`.
- 관련: [ADR-0001](0001-contract-driven-foundation.md), [구현 안내 · 클라우드 사이 직접 인계](../contract-foundation.md), 명세 FR-10, §15.3.

## 맥락

계약의 `security.required_controls`(교차 tenant 거부, 전송 암호화, 감사, 복원 시험 등)는 목적지 통제 시험(`target_control_test`)이 된다. v1 컴파일러는 이 의무를 모두 **활성화 의도 기록** 단계(`record_activation_intent`)에 두었다. 이 단계는 쓰기 정지(접수 정지)와 활성화 사이에 있다. 그래서 통제 시험이 업무 쓰기가 멈춘 구간 안에서 측정됐다.

실측에서 이것이 정지 시간의 대부분이었다. 클라우드 사이 경로(RDS → Cloud SQL, 1만 행)에서 복사는 4.6초에 끝났다. 그런데 최종 검증 뒤 활성화까지 14초가 더 걸렸다. 그 대부분이 `tested_restore` 복원 훈련이다. 복원 훈련은 목적지 표 전체를 이 기기를 거쳐 다른 DB로 다시 옮긴다.

## 명세

- FR-10 "목적지 구성·보안 기능 검증 — 허용·거부·감사·복원 시험"은 목적지 준비에 속한다.
- §15.3 단계 표:
  - `TARGET_PREPARED`: 대상 인프라·데이터 구조·신원·관측·백업 준비.
  - `CUTOVER_READY`: 계획·승인·자원·**증거**·용량 **재확인**. 다음 단계 조건은 "모든 필수 조건 유효".
  - `QUIESCING` 이후는 요청·작업 정리, 차단, 최종 비교, 활성화 의도다.

명세는 목적지 통제를 정지 구간 안에서 다시 **측정**하라고 하지 않는다. 정지 직전에 증거가 **유효**한지 재확인하라고 한다.

## 결정

1. 목적지 통제 의무는 **쓰기 정지 직전 단계**에서 측정한다.
   - offline-copy: 목적지 준비(`stage_target`)
   - snapshot-cdc: 컷오버 확인(`check_cutover_ready`). 초기 동기화가 끝나 목적지에 거의 최종 데이터가 있다.
   - failback: 복귀 대상 확인(`verify_return_target`)
   - 예외: 시험에 옮겨진 데이터가 있어야 하는 통제(`tested_restore` 복원 훈련)는 쓰기 정지 전에 데이터가 목적지에 닿는 템플릿에서만 앞으로 옮긴다. snapshot-cdc처럼 동기화 단계가 있는 템플릿이 그렇다. offline-copy는 정지 전 목적지가 비어 있어, 그 시점의 복원 훈련은 아무것도 증명하지 못한다. 그래서 지금처럼 활성화 의도 단계에서 잰다. 계정 단위 시험이 처음 구현의 이 빈틈을 잡았다(계정 0개로 한 복원 훈련을 FAIL로 판정).
2. 같은 의무를 활성화 의도 단계에 `still_valid_at`으로 다시 묶는다. 그 단계의 필수 증거(`required_evidence`)에 들어가지만 다시 측정하지 않는다. 조정자는 기존 증거로 판정한다.
   - 증거가 만료됐거나 FAIL이면 활성화 의도가 막힌다.
   - 그 사이 목적지에 변경 사건이 있으면 변경 영향 판정이 재평가를 요구한다.
3. 최종 데이터로 하는 복원 시험(`operations.restore_test`)은 지금처럼 활성화 뒤 안정화 단계에 둔다.
4. 계획 의미가 바뀌므로 컴파일러 버전을 `v2`로 올린다. v1 계획은 v1 의미 그대로 저장·검증된다.

## 결과

- 정지 구간 안에는 차단 증명, 최종 내용·업무 비교, 활성화 의도와 그 증거 유효성 재확인만 남는다.
- 목적지 통제가 실패하면 쓰기를 멈추기 **전에** 보류된다. 예전에는 정지한 뒤 활성화 직전에 보류돼 원본을 다시 열어야 했다.
- 비용: 통제 증거의 측정 시점과 활성화 사이가 길어진다. 그 사이 목적지 변화는 변경 수집기와 증거 만료가 막는다. 수집기가 없는 환경에서는 증거 유효 기간을 짧게 둔다.

## 측정

같은 조건(1만 행, 경로마다 5회, `tests/perf/test_cloud_handoff_pause.py`)에서 변경 전후를 비교했다. 시각이 다른 두 측정이므로 네트워크 차이도 섞여 있다.

| 경로 | 전: 최소 / 중앙값 / 최대 (ms) | 후: 최소 / 중앙값 / 최대 (ms) |
|---|---|---|
| RDS → Cloud SQL (offline-copy) | 13556 / 20226 / 21222 | 11295 / 11525 / 12378 |
| Cloud SQL → RDS (offline-copy) | 12386 / 13998 / 17607 | 11433 / 12442 / 13382 |
| Cloud SQL → 로컬 (snapshot-cdc, 논리 복제) | 7959 / 11477 / 14581 | 5889 / 6002 / 6103 |

- snapshot-cdc는 복원 훈련까지 정지 구간 밖으로 나가 중앙값이 절반 가까이 줄었고, 편차도 크게 줄었다.
- offline-copy는 데이터와 무관한 통제만 나갔다. 원격 목적지에서는 이 시험들도 연결마다 인터넷 왕복이 들어 비용이 컸다. 남은 7~8초는 정지 구간 안에 남긴 복원 훈련이다. 더 줄이려면 별도 설계가 필요하다. 예를 들어 복원을 목적지 서버 안에서 하거나, 정지 전 리허설(§15.3 `TARGET_PREPARED`의 "리허설 통과")로 대신하는 방식이다.
