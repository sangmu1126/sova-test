# ADR-0002 · 계정 이전을 인계 계획 안으로 넣는 방법

- 날짜: 2026-11-15
- 상태: **채택(C)**, 2026-11-15. 구현과 검증은 아래 [결정](#결정)과 [구현](#구현)에 있다.
- 관련: [ADR-0001](0001-contract-driven-foundation.md), [구현 안내 · Identity 확장](../contract-foundation.md), 명세 Part II §7~§9.

## 맥락

계정 이전(`KeycloakIdentityMigration`, 원본은 Keycloak 또는 Cognito)은 지금 컴파일된 인계 계획 **밖**에서 실행된다.

안전은 지켜진다. 계약의 Identity 의무(IAM-02·04 등)가 활성화 의도 단계에서 서명 증거로 통과해야 하므로, 계정 이전과 사용자 재설정이 끝나지 않으면 데이터 인계는 활성화되지 않는다. AWS 전체 탈출도 이 구조로 통과했다.

다만 다음 세 가지가 빠져 있다.

1. **승인 결속:** 승인자는 데이터 인계 계획의 digest를 승인한다. 계정 이전이라는 외부 효과는 그 승인에 묶이지 않는다.
2. **효과 원장:** 계정 이전은 효과 원장의 의도 기록·불명 효과·복구 리스·읽기 전용 조정을 거치지 않는다. 응답이 유실되면 사람이 다시 실행해야 한다.
3. **잠금:** 같은 계정 집합을 두 계획이 동시에 옮기는 것을 계획 간 충돌 판정이 보지 못한다.

## 제약

- 인계 권한 상태기계와 세 템플릿의 유계 모델 검사는 계속 통과해야 한다. 상태를 늘리면 모델 검사 대상도 함께 늘어난다.
- 계획 하나는 지금 manifest 하나(adapter 하나)에만 묶인다.
- 계정은 비밀번호·MFA 없이 옮겨진다. 목적지 로그인은 사용자 재설정 뒤에야 가능하다. 그래서 "계정 복사 = 즉시 활성화"가 아니다.
- failback 계획에 계정 역이전은 없다. 인계 뒤 목적지에서 새로 생긴 계정을 원본으로 돌려보낼 수단도 없다.

## 선택지

### A. 지금 구조 유지(선행 작업 + 증거 게이트)

- 바꾸는 것: 없음. 문서에 "계정 이전은 별도 승인·실행"으로 명시한다.
- 장점: 핵심부 변경이 없다. 안전 성질은 이미 시험됐다.
- 단점: 위 1~3이 그대로 남는다.

### B. 데이터 계획에 계정 이전 단계를 추가(다중 adapter 계획)

- **템플릿:** Identity 확장이 `MIGRATE_IDENTITY`일 때 `stage_target` 다음에 `migrate_identities` 단계를 넣는다. 단계는 상태를 공유할 수 있으므로(예: `copy_content`가 `fence_source_writes`와 같은 `SOURCE_FENCED`를 쓴다) 이 단계도 `TARGET_PREPARED`를 공유하게 한다. 그래서 새 권한 상태는 만들지 않는다.
- **컴파일러:** 단계마다 manifest를 고르게 한다(데이터용, Identity용). 방향별 자격도 adapter마다 따로 판정한다(예: Cognito → Keycloak 프로필의 자격).
- **내리기·충돌:** `_SIDE`에 새 단계를 `target`으로 추가한다. 잠금 집합에 목적지 realm과 원본 directory를 넣는다.
- **실행:** 실행기는 명령의 `adapter_id`로 adapter를 고르는 등록부를 쓴다. 효과 원장 계약은 그대로다.
- **failback:** Identity 확장이 있는 계획의 failback은 계정 역이전 수단이 생길 때까지 `UNSUPPORTED`로 막는다.
- 장점: 1~3이 모두 해결된다. 승인 하나에 데이터와 계정이 함께 묶인다.
- 단점: 컴파일러·자격 판정·내리기·실행 등록부를 함께 바꿔야 한다. 계획 하나의 실패 원인이 두 종류의 외부 시스템으로 늘어난다.

### C. 계정 집합을 독립된 인계 단위로(같은 프로토콜, 단위 간 순서 제약)

- 계정 집합을 하나의 이전 단위로 보고, 같은 템플릿과 권한 프로토콜로 인계한다. 각 단계는 다음에 대응한다.

| 단계 | 계정 집합에서의 효과 |
|---|---|
| 목적지 준비 | 목적지 realm, 관리자 전용 원본 subject 속성 |
| 신규 접수 정지 | 원본의 셀프 가입 중지 |
| 원본 차단 | 원본의 계정 변경 차단 |
| 복사 | 계정 이전 |
| 최종 검증 | IAM-01·06 |
| 활성화 | 목적지 로그인 허용 |
| 경로 확정 | 앱의 발급자 설정 전환 |

- 데이터 단위의 활성화 의도는 Identity 단위의 완료 증거를 요구한다. 이것은 단위 간 순서 제약으로, 새로 필요하다.
- 장점: 권한 프로토콜·adapter 적합성 시험·효과 원장을 그대로 쓴다. 계획 하나가 adapter 하나라는 지금 구조를 지킨다. 계정 쪽 failback도 같은 틀로 다룰 수 있다.
- 단점:
  - 단위 간 순서 제약을 새로 만들어야 한다.
  - Cognito에는 "계정 변경 차단"을 정확히 거는 기능이 없다. 셀프 가입 중지와 관리 API 권한 회수로 근사하게 되며, 그 근사의 한계를 자격 판정에 적어야 한다.
  - 원본 차단 시간이 길어지면 사용자 영향이 크다.

## 추천

**C.** 계획 하나 = adapter 하나 = 권한 기록 하나라는 지금의 단순성을 지키면서, 승인 결속·효과 원장·잠금을 모두 얻는다. 지금까지 쌓은 adapter 적합성 시험을 Identity adapter에도 그대로 적용할 수 있다.

B는 승인 하나로 묶이는 편의가 있다. 하지만 실패 원인과 자격 판정이 한 계획에 섞이고, 한쪽 실패가 다른 쪽의 보류로 번진다.

A는 지금 당장 안전하므로, C를 구현하기 전까지의 상태로 유지한다.

## 결정

C를 채택한다. 열린 질문(아래)은 다음과 같이 정했다.

1. **단위 간 순서 제약의 표현.** 계약 스키마(Identity v1)는 바꾸지 않고 컴파일 규칙으로 표현한다.
   - 규칙: 원본 IdP를 제거하는 계약(`MIGRATE_IDENTITY`)이고 의존성 그래프에 `identity` 종류 노드가 있으면, 데이터 단위 계획에 `identity.unit_handoff_complete` 의무를 둔다.
   - 의무의 자리: 활성화 의도 기록(`record_activation_intent`).
   - 의무에 담는 것: 계정 단위의 `unit_digest`와 구성원. 컴파일러가 같은 계약·snapshot으로 계정 단위의 경계를 다시 계산해 정한다.
   - 검증: 검증자가 그 단위의 현재 권한 기록이 `HANDOFF_COMPLETE`인지 읽는다.
   - 계획 수용 단계에서 확인하지 않는 이유: 수용은 한 번뿐이지만 활성화는 그보다 한참 뒤일 수 있다. 활성화 직전에 서명 증거로 확인해야 한다.
2. **Cognito의 원본 차단.** 이번에는 Keycloak 원본만 독립 단위로 구현했다. Cognito 원본은 계속 A(선행 작업 + 증거 게이트)로 다룬다. 근사 차단(셀프 가입 중지 + 관리 API 회수)을 자격으로 인정할지는 Cognito 단위 adapter를 만들 때 정한다.
3. **인계 뒤 목적지에서 생긴 계정의 failback.** 지원하지 않는다. 계정 단위 계획의 failback은 컴파일러가 `IDENTITY_UNIT_FAILBACK_UNSUPPORTED`(UNSUPPORTED)로 막는다.
4. **사용자 재설정 완료 비율.** 활성화 조건으로 두지 않는다. 재설정은 각 사용자의 다음 로그인 때 일어나므로, 조건으로 두면 활성화가 끝없이 미뤄진다. IAM-02는 지금처럼 표본 사용자 기준이다.

그래프에 `identity` 노드가 없으면 계획은 이전과 똑같다. 계정 이전은 계획 밖(A)에 남는다. 등록된 의존성 목록이 IdP를 노드로 담을 때부터 C가 적용된다.

## 구현

- **컴파일러.** 단위 구성원이 모두 `identity` 노드이면 계정 단위다.
  - 계정 단위에서는 데이터 내용 비교·업무 불변식·외부 효과 의무를 만들지 않는다. 계정 비교는 IAM-01·06이 맡는다.
  - 목적지 로그인은 이 단위의 활성화에서야 열린다. 그래서 IAM 흐름 시험(IAM-02·03·04)은 `stabilize`로 옮긴다.
  - 데이터 단위는 위 순서 의무를 받는다.
  - `MIGRATE_IDENTITY`가 아닌 계약에서 계정 단위를 요청하면 UNSUPPORTED다.
- **경계 분석.** 서비스가 `identity` 노드를 `calls`·`uses`로 부르는 관계가 단위 경계를 넘을 때, `MIGRATE_IDENTITY`이면 미정 효과로 막지 않는다. 그 의미(발급자 전환, 순서 제약)를 계정 단위 프로토콜이 정하기 때문이다. 그 밖의 경우는 이전처럼 막는다.
- **잠금.** 계정 단위의 경로 키는 앱이 신뢰하는 발급자(`route/identity`)다. 데이터 경로(`route/unit`)와 다르다. 그래서 한 서비스의 두 단위는 서로 막지 않는다. 같은 IdP를 옮기는 두 계획은 원본 IdP의 쓰기 정책 키에서 충돌한다.
- **adapter.** `KeycloakIdentityHandoff`는 두 템플릿의 모든 단계를 구현한다.
  - writer는 셀프 가입·사용자 본인 프로필 수정(앱)과 사용자 관리 권한을 가진 백오피스 client(다른 writer)다.
  - 차단: 셀프 가입·본인 수정을 막고 백오피스 권한을 회수한다. readback은 IdP 중개 로그인·사용자 연합처럼 계정을 만드는 다른 경로가 켜져 있거나, 프로필을 바꾸는 미완료 필수 동작을 가진 계정이 있으면 차단을 확인하지 않는다.
  - 차단 전 설정은 원본 realm에 남긴다. 중단 때 `restore_source()`로 되돌린다.
  - 계정 복사는 기존 `KeycloakIdentityMigration`이 한다.
- **독립 probe.** `KeycloakWriterProbes`는 adapter와 코드를 공유하지 않는다. 가입 폼 제출과 백오피스 사용자 생성을 실제로 시도하고, 만든 계정을 지운다.
- **순서 검증자.** `UnitCompletion`(application)이 권한 저장소에서 선행 단위의 현재 기록을 읽는다.

검증(로컬, 2026-11-15):
- 컴파일 규칙·잠금 단위 시험 5개.
- adapter 공통 적합성 시험과 중단·IdP 중개·독립 probe 시험 12개. 실제 Keycloak 두 대에서 돌렸다.
- control plane 두 단위 시험 2개.
  - 계정 단위가 최종 검증까지만 하고 멈췄을 때: 데이터 단위는 매핑 의무를 통과하지만, 활성화 의도에서 순서 의무가 실패해 목적지가 활성화되기 전에 보류된다.
  - 계정 단위가 끝난 뒤: 데이터 단위도 완료되고, 두 단위의 권한 기록이 각자 `HANDOFF_COMPLETE`다.
- 세 템플릿은 바뀌지 않았으므로 권한 상태기계의 유계 모델 검사 대상도 그대로다.

## 결정 전 열린 질문 (기록)

1. 단위 간 순서 제약의 표현: 계약의 의존성 그래프에 선언하는가, 계획 수용 단계에서 다른 단위의 완료 증거로 확인하는가.
2. Cognito의 "원본 차단"을 셀프 가입 중지와 관리 API 회수로 근사하는 것을 자격으로 인정할지. 이 근사 아래에서 활성화 전 마지막 동기화를 다시 해야 하는지.
3. 인계 뒤 목적지에서 생긴 계정의 failback. 지원하지 않는다고 막을지, 역동기화 adapter를 둘지.
4. 사용자 재설정이 끝나지 않은 계정의 비율을 활성화 조건으로 둘지. 지금은 IAM-02가 표본 사용자 기준이다.

## 검증 계획(C를 택할 때, 결정 전 기록)

- Identity adapter가 템플릿 동작(목적지 준비·접수 정지·차단·복사·검증·활성화·경로 확정)을 구현하고 [adapter 공통 적합성 시험](../contract-foundation.md)을 통과한다.
- 원본이 Keycloak인 로컬 경로와 원본이 Cognito인 실계정 경로를 둘 다 시험한다.
- Identity 단위가 완료되지 않았으면 데이터 단위의 활성화 의도가 거부되는 것을 시험한다.
- 세 템플릿과 Identity 단위의 유계 모델 검사가 통과한다.
