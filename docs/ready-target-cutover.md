# 준비된 목적지의 정상 전환과 작업자 장애 복구 분리

2026-11-19 · 개인 브랜치 `feature/migration-request-qualification`.

## 구분이 필요한 이유

기존 v2 HTTP 시험은 경로 효과가 실행 중일 때 소유 작업자를 멈추고, 그 뒤 목적지 Pod의 선택 라벨을 활성화한다. lease 만료만으로 살아 있는 작업자를 대체하지 않는지, 실제 종료 뒤 조회 전용 복구가 가능한지를 검증하기 위한 장애 조건이다. 이 결과를 이미 준비된 목적지로의 정상 전환 성능으로 해석하면 안 된다.

새 v3는 목적지 Pod와 `side=target` 라벨을 **작업 접수 전에** 준비한다. 출발지 Service는 계속 `side=source`를 선택한다. 목적지의 상태 확인 성공과 쓰기 권한은 별개이며, 실제 전환 전 목적지 앱 역할의 INSERT가 SQLSTATE `42501`로 거부되는지 확인한다.

| 조건 | 정상 전환 v3 | 기존 장애·복구 v2 |
|---|---|---|
| 목적지 Pod 준비 | 접수 전 완료 | prepared 경로는 접수 전 완료 |
| 목적지 선택 라벨 | 접수 전 `target` | 원 작업자를 멈춘 뒤 활성화 |
| 측정 중 작업자 고장 | 주입하지 않음 | 실제 CRI pause·lease 만료·정상 Pod 삭제 |
| 완료 근거 | 실제 워커의 완료·효과 확인·경로 PATCH 1회·복구 이벤트 0건 | 살아 있는 소유자 복구 거부·실제 종료·후속 워커 조회 전용 복구 |
| 공통 검증 | 실제 HTTPS 요청, 권한 거부, 고정 이미지 바이트, 신규·기존 주문 SQL 대조 | 동일 |

두 프로필은 고장 조건이 다르다. 수치를 동일 조건의 성능 개선율로 비교하지 않는다. 새 정상 경로를 추가해도 기존 장애 시험을 제거하거나 성공 기준을 완화하지 않는다.

## 실행과 관측

두 실제 CLI 워커 Pod가 기존 계획·승인·소유권·효과 원장을 통해 실행한다. 정상 전환 시험은 워커를 멈추거나 삭제하지 않는다. 수동 목적지 활성화 호출도 0회여야 한다. Kubernetes 감사 로그에서 경로 PATCH의 실제 SA UID와 Pod UID를 확인하고, 같은 목적지 Pod가 최초 부하 중 실제 업무 응답을 반환하는지 검사한다. 완료 뒤 생성되는 확인 요청 3건만으로 전환 중 업무 성공을 대신하지 않는다.

클라이언트는 단일 closed-loop 방식으로 주문 100건을 보내고, 완료 뒤 확인 주문 3건을 추가한다. 각 요청은 새 연결을 사용하며 think time은 0.2초다. `ready_deferred`는 실패 주문을 부하 종료 뒤 복구한다. `ready_bounded`는 기존과 같은 5초·총 8회(조회 포함)·시도별 네트워크 1초 한도를 사용한다. 제한 소진과 후속 복구는 별도로 기록한다. 최초 오류와 404 조회도 지우지 않는다.

제품 소스·이미지·DB 연결 제한·클라이언트 시간 및 횟수 한도는 변경하지 않았다. 시험 fixture·프로필만 추가했다.

새 비공개 출력 경로와 고정 security checkout을 지정해 실행한다. 고정 서비스·노드 이미지가 로컬에 없으면 다른 버전으로 대체하지 않는다. 실제 사용한 전체 SHA는 개발 기록에 있다.

```sh
python tests/qualification_postgres.py --suite pod-http --http-mode ready_bounded \
  --image sha256:0d938e975177bef9f1f61f3f9dbcf2e0aa0a139568f66d3415ed8892eb97f6ac \
  --security-source <pinned-security-checkout>/src --artifacts <new-private-directory>
```

`ready_deferred`는 정상 전환·부하 후 복구, `prepared_deferred`는 기존 작업자 중단·복구 대조다. 모드마다 새 출력 디렉터리를 사용한다.

## 이번 실행 결과

| 경우 | 최초 실패 / 100건 | 호출 내 제한 재시도 | 최종 SQL | 환경 검증 |
|---|---:|---|---|---|
| 정상 전환·부하 후 복구 | 7 (source 503) | 미사용 | 103/103 | 시계 감시 통과 |
| 정상 전환·제한 재시도 | 2 (source 503) | 완료 99·횟수 소진 1 | 후속 복구 뒤 103/103 | 시계 감시 통과 |
| 기존 작업자 장애 대조 | 21 (503 16·통신 5) | 미사용 | 103/103 | **시계 관측 1회 실패·전체 인수 불가** |

정상 전환 두 경우는 실제 워커의 복구 이벤트 없이 완료됐고, 최초 부하 중 target 200 응답을 각각 81·80건 확인했다. bounded 소진 1건은 5초가 아닌 총 8회 한도 때문이며 최대 호출 시간은 2.964초였다. 후속 복구까지 포함한 최대 부하 주문 완료는 25.026초다. 한도 전체 충족이나 무오류로 기록하지 않는다.

장애 대조의 기능 시험은 통과했지만 시계 관측 실패의 원인은 미확정이다. 정상 관측값으로 실패 구간을 메우지 않으며 해당 runner의 종료 코드 1과 원문을 보존한다. 세 실행의 시험 전용 컨테이너·네트워크 이름 12개가 정리됐음을 별도로 확인했다.

[시계 관측 진단 후속 작업](clock-observation-diagnostics.md)에서 비밀값 없는 시각·단계·예외 분류와 불완전 감시 거부를 추가했다. 새 대조의 관측 성공은 위 실패의 삭제나 원인 해결 판정으로 사용하지 않는다.

[조회 backpressure 후속 비교](lookup-backpressure.md)에서는 별도로 발견한 복원 스냅샷 경합을 수정한 새 이미지에서 두 모드를 실행했다. 조회의 1초 안내를 연결해도 호출 한도 소진 1건은 남았다. 이 문서의 기존 실행·이미지·오류 수치를 새 결과로 대체하지 않는다.

## 판정 범위

Ready 상태가 경로 전파 지연 0초를 증명하지 않는다. source 쓰기 차단 중 503이나 연결 오류가 실제로 발생할 수 있다. 최종 SQL 일치가 최초 응답 성공이나 요청별 완료 한도 충족을 의미하지도 않는다.

계획과 게이트에 전달하는 일부 증거는 시험 fixture 입력이다. 그중 `availability.client_completion_wait=pass`나 실행 상태 `HANDOFF_COMPLETE`를 이번 실측 클라이언트의 완료 한도 통과로 해석하지 않는다. 실제 요청·제한 소진·SQL 대조는 별도 결과로 기록하며, 충돌할 때 운영 무중단을 주장하지 않는다.

대상은 로컬 arm64 kind 한 노드와 전용 PostgreSQL 서버의 별도 DB다. 계획·IdP·초기 설정은 합성 입력이며, 원장은 로컬 fixture 파일을 사용한다. 실제 네트워크·TLS·Kubernetes·SQL을 사용하지만 AWS→독립 온프렘 이전이나 운영 부하, WORM, 기업 인증, 금융 보안 인증을 검증한 것은 아니다. 각 경우 1회 실행으로 통계적 SLO를 발급하지 않는다.
