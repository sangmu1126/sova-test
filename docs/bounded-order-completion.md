# 목적지 사전 준비와 한도 있는 주문 완료

2026-11-19 · 개인 `feature/migration-request-qualification`.

## 변경 내용

기존 실환경 시험에서 주문은 보존됐지만, 첫 HTTP 요청이 실패한 뒤 부하가 끝날 때까지 재시도를 미뤘다. 이번에는 **목적지 준비 지연**과 **실패 요청의 완료 정책**을 나눠 비교한다. 서버 오류를 성공으로 덮어쓰거나 승인·쓰기 차단을 해제하는 변경은 없다.

추가한 `sova.qualification.bounded_orders.BoundedOrderClient`는 다음 계약을 가진 주문 API용 측정 클라이언트다.

- POST는 같은 customer·idempotency key에 대해 원자적으로 한 결과만 만든다.
- GET은 그 키의 커밋 결과를 권위 있게 조회한다. 캐시된 조회나 다른 replica의 오래된 404로 대신하지 않는다.
- 응답 영수증은 요청의 customer·키·금액과 일치해야 한다.
- 출발지와 목적지의 단일 writer 보장은 기존 실행기·fencing이 담당한다. 재시도는 그 보장을 만들지 않는다.

이 조건이 없는 임의 API의 POST에 자동 재시도를 적용하는 기능이 아니다. 서버 측 쓰기 버퍼·내구성 작업 큐·운영 가용성 게이트웨이도 아니다.

## 재시도 규칙

| 상황 | 다음 동작 |
|---|---|
| 유효한 성공 영수증 | 확인 완료 |
| HTTP 503 또는 연결/응답 오류 | 같은 키로 먼저 조회 |
| 조회 200 + 유효한 영수증 | POST를 반복하지 않고 완료 |
| 조회 404 | 같은 내용·키로 POST 허용 |
| 401·403·409·429·500·redirect 등 | 헤더 상태로 중단, 오류 본문을 기다리며 통신 오류로 바꾸지 않음 |
| 잘못된 성공 영수증 | 중단, 확인 완료로 처리하지 않음 |
| 지원하는 Retry-After | 대기 시간보다 일찍 다시 보내지 않음. 조회 404의 힌트도 적용 |
| 지원하지 않는 Retry-After 형식 | 임의로 무시하지 않고 중단 |
| 기한·횟수 소진 | EXHAUSTED. 커밋 여부를 추정하지 않음 |

기본 한도는 **호출당 5초·최대 8회(조회 포함), 각 네트워크 시도 최대 1초**다. 0~지수 backoff 상한 사이의 full jitter를 쓰며 최대 backoff는 0.5초다. 시험에서는 비교용 seed 0을 고정한다. 일반 사용의 기본 난수기는 별도다.

`Retry-After`는 delta-seconds를 지원한다. 날짜 형식 등 미지원 값은 중단한다. 서버가 요구한 대기가 남은 기한을 넘으면 기한을 늘리거나 조기 재전송하지 않는다.

기한은 연결·헤더·응답 본문을 포함하는 비동기 네트워크 구간을 취소한다. read timeout을 매 바이트마다 새로 시작하는 방식으로 느린 응답이 기한을 늘리지 못한다. 원장 저장 후에도 남은 시간을 다시 확인해, 저장 중 기한이 지났으면 HTTP transport를 호출하지 않는다. 로컬 디스크·스케줄러·관측 callback까지 hard real-time으로 보장하는 것은 아니다.

`attempts`는 원장에 예약한 시도 수이며 `transport_calls`는 실제 transport 진입 수다. 기록 직후 기한이 소진되면 두 수가 다를 수 있다. 모든 시도는 기존 SQLite 원장에 남고, 관측 이벤트에는 실제 transport 진입 여부도 구분한다.

`REJECTED`는 **재시도 정책이 멈췄다는 뜻**이다. 서버에서 주문이 커밋되지 않았다는 판정이 아니다. 영수증·최종 DB 대조 없이 EXHAUSTED나 REJECTED를 데이터 미커밋으로 취급하면 안 된다.

## 실제 비교 조건

[전용 v2 프로필](../examples/qualification/orders-pod-https-comparison-v2.json)에 다음 세 경우를 명시했다.

1. `cold_deferred`: 워커 중단 후 목적지 앱을 기동하고, 실패 주문은 부하 종료 후 복구한다.
2. `prepared_deferred`: 목적지 HTTPS health를 먼저 준비하되, 실패 복구 방식은 그대로 둔다.
3. `prepared_bounded`: 같은 사전 준비 상태에 한도 있는 주문 완료 정책을 적용한다.

각 경우 측정 부하는 **정확히 100건**이며, 전환 완료 뒤 대상 응답을 확인하는 별도 주문 3건을 추가한다. 최종 데이터 대조는 총 103건을 다루고, 별도 확인 3건을 최초 성공률이나 재시도 수에 섞지 않는다. 같은 고정 제품 이미지·프로필·HTTPS Service·원본 스키마·실제 워커 중단/복구 조건을 사용하며, 각 실행은 독립된 새 DB·클러스터다. Service는 각 실행 안에서 UID·NodePort·URL을 유지하며, 세 실행이 같은 물리 Service를 공유하지 않는다. 단일 closed-loop client가 논리 요청 처리 후 0.2초를 기다린다. 따라서 재시도로 대기하는 경우 최초 요청의 실제 도착 시각·제공 부하는 달라진다. 동일한 open-loop 부하나 통계적 개선율로 해석하지 않는다.

사전 준비는 이미지·HTTPS 프로세스의 준비다. 실제 Service에는 아직 선택되지 않는 라벨을 사용한다. 출발지의 양성 대조 `SELECT 1` 성공과 목적지의 쓰기 권한 거부(SQLSTATE 42501)를 확인하며, 쓰기를 일찍 열지 않는다. 기존 효과가 진행 중일 때 워커를 중단하는 조건을 유지하기 위해, 중단 후 준비된 Pod를 target 라벨로 노출한다.

## 측정값 해석

| 지표 | 기준 | 제외하면 안 되는 것 |
|---|---|---|
| 최초 오류 | 부하 100건의 첫 POST 중 200을 받지 못한 수 | 후속 재시도가 성공해도 최초 503·통신 오류는 유지 |
| 기한 내 완료 | bounded 호출이 반환한 CONFIRMED·EXHAUSTED·REJECTED | 부하 종료 뒤 복구된 주문을 inline 성공에 합치지 않음 |
| 실제 전송 수 | load·inline_retry·recovery·post_handoff_probe를 구분 | 조회도 전송 수와 재시도 한도에 포함 |
| 최종 논리 완료 시간 | 최초 intent부터 확인 영수증까지 같은 클라이언트 시계로 계산 | 부하 종료 뒤 기다린 시간과 재시도 시간 포함 |
| 데이터 대조 | 측정 100건 + 별도 확인 3건, 독립적인 목적지 SQL 관측 | 중복 주문·누락·미완료 시도·불일치 영수증 |

이 클라이언트는 가용성 개선의 한 수단이다. 쓰기 중단이 5초보다 길면 모든 요청을 5초 안에 성공시킬 수 없다. 더 오래 기다리려면 업무 요구에 따른 별도 한도, 서버 측 내구성 대기, 취소·만료 의미와 사용자 응답 계약을 먼저 정해야 한다. 한도를 임의로 늘려 시험을 통과시키지 않았다.

## 검증 결과

**전체 3종 비교는 미완료다.** 시험 스냅샷 `7ce0b4c`와 동일 제품 이미지로 각 경우를 한 번씩 독립 실행했다.

| 경우 | 최초 요청 오류 / 100건 | 최종 결과 |
|---|---:|---|
| 목적지 후속 기동 + 부하 종료 뒤 복구 | 37 | 복구 후 상태 조회 HTTP 500. 시계 표본 수집 실패 1건도 있어 비교 인수 실패 |
| 목적지 사전 준비 + 부하 종료 뒤 복구 | 18 | 최종 SQL 대조 103/103 확인. 기존 주문 50건 유지. 부하 주문 최대 완료 시간 23.068초 |
| 목적지 사전 준비 + 제한 재시도 | 5 | 클라이언트 내 CONFIRMED 97·EXHAUSTED 3. 워커 완료 상태 90초 시간 초과. 독립 최종 SQL 대조 미완료 |

이 수치는 동일 도착 부하에 대한 개선율이 아니다. 특히 마지막 경우는 주문별 클라이언트 영수증 관측과 전체 이전 완료를 구분해야 한다. 최대 inline 호출 시간은 5.129초였으며, 로컬 원장 저장·정리까지 hard real-time으로 제한한 결과가 아니다. 실패·소진 호출은 완료 지연 목표를 충족한 것으로 세지 않는다.

제한 재시도 실행의 client는 부모 완료 신호 없이 120초 부하 상한으로 종료했다. 당시 fixture가 보낸 후속 복구·확인 요청의 phase 이름은 실제 handoff 완료를 증명하지 않는다. 이후 `a0d087b`에서 **검증된 부모 완료 신호 없이는 후속 복구·확인 요청을 보내지 않도록** 수정했다. 이 기록의 시점에는 사후 하네스 수정으로 3종 클러스터 비교를 재실행하지 않았다. 이후 재실행과 별도의 실패·통과 결과는 아래 후속 수정 기록에 연결한다.

단위 92건·실제 loopback TCP 2건은 통과했고, 이미지 설치 바이트 440개가 일치했다. 이 통과와 실패한 클러스터 비교를 합쳐 “전체 통과”로 표시하지 않는다. 이번 실행 전용 컨테이너·네트워크 44개 이름의 부재를 읽기 전용으로 재확인했다. 재현용 캐시 이미지는 보존했다.

5초/8회 한도를 소진한 호출은 `EXHAUSTED`로 남는다. 이후 부하 종료 후 복구해 데이터가 일치해도 `completion_budget_satisfied`는 false다. fixture 통과는 소유권·거부 경계·최종 데이터 대조 검증이며, 모든 주문의 기한 내 완료를 의미하지 않는다.

## 범위와 재현

```sh
caffeinate -di python tests/qualification_postgres.py \
  --suite pod-http --http-mode prepared_bounded \
  --image sha256:0d938e975177bef9f1f61f3f9dbcf2e0aa0a139568f66d3415ed8892eb97f6ac \
  --security-source /path/to/security-at-27e6e855/src \
  --artifacts /path/to/new-private-run-directory
```

`--http-mode`만 바꿔 나머지 두 경우를 실행할 수 있다. 제품 소스 `3d724ba014156557f3bd9706160f2d7ae510d27c`와 security 소스 `27e6e85514a7cbb3e43d216464b72d9bd78f3fcf`로 만든 최종 arm64 이미지 ID는 `sha256:b99f136eb590d2df900f3ea2bdddb5df244031315917aed6fbc71907cd331bf7`다. 설치 Sova 318개·security 122개 파일과 엔트리포인트를 실제 이미지 및 Pod에서 대조한다. 이 ID는 로컬 Docker 이미지 ID이며 레지스트리 서명·게시 digest와 동일한 주장으로 사용하지 않는다. CRI imageID가 다를 수 있으므로 Pod에서는 설치 바이트 대조도 함께 수행한다.

원문 로그·SQLite·빌드 입력은 비공개 로컬 실행 디렉터리에 보존하고, 공개 증거에는 요약과 원문 해시를 기록한다. 해시는 원문 배포나 서명된 운영 증명을 대신하지 않는다. Dockerfile의 전이 의존성은 범위 지정이므로 같은 소스의 재빌드가 같은 이미지 ID가 된다고 보장하지 않는다. 서명·SBOM·취약점 재검사를 통과한 릴리스라는 주장도 하지 않는다.

 전용 kind와 client·DB·네트워크만 생성하고 정리하며 기존 클러스터·사용자 kubeconfig·AWS는 변경하지 않는다. 고정 캐시 이미지가 없으면 다른 버전으로 대체하지 않는다.

지금 기능은 명시적으로 사용하는 qualification 클라이언트와 시험 경로에 적용됐다. 기존 동기 `OrderHttpClient`의 기본 동작이나 제품의 승인·worker·adapter·domain·스키마는 바꾸지 않았다. 일반 앱의 SDK·프록시·서버 측 쓰기 대기와의 운영 연결은 별도다.

계획·IdP·witness·DB 인증의 fixture 한계, 단일 node/server, 장기 연결·WebSocket·운영 NetworkPolicy·AWS→독립 온프렘·WORM·공급망·생산 부하/SLO 미검증은 남는다. 이 실험으로 무중단·금융 보안 인증·실행 승인을 발급하지 않는다.

## 복구 조회 후속 수정

[복구 상태 조회와 증인 기록의 동시성](authority-read-concurrency.md)에서 미커밋 SQL·외부 증인 대조, 프로세스 간 파일 기록 경합을 별도로 재현하고 수정했다. 새로운 실제 Pod 결과와 남은 환경 실패는 해당 기록에서 구분한다. 이 문서의 기존 고정 실행·오류·소진 수치는 후속 성공으로 덮어쓰지 않는다.

[준비된 목적지의 정상 전환](ready-target-cutover.md)은 작업자 장애를 주입하지 않는 별도 v3 프로필이다. 기존 v2 장애·복구 경로와 구분하며 동일 조건의 성능 개선 비교로 사용하지 않는다.
